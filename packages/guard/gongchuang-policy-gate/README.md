# @gongchuang/client-policy-gate

English | [中文](README.zh.md)

## Summary

The Host-root fork listener copies only product-imported document references in inherited user messages before a cross-workspace child is created. Identical target files may be reused; differing same-name files, missing sources and escaping paths fail without overwriting files or archiving the source conversation. Completed copies remain reusable after an I/O interruption. Arbitrary workspace outputs are not synchronized.

Private product guard for 共创企业助手. The signed desktop host supplies an exact-byte Ed25519 policy envelope, pins the policy public-key digest in host code, and binds the active Host-verified skill suite's professional delivery contract and call graph into the same composition. This native Cordis plugin independently rejects a replacement policy key before verifying and freezing policy at load, rejects provider drift before the first request, routes every tool call through allow/ask/deny policy, and requires professional tasks to activate the active suite's owning skill, hard dependencies, and quality checks. Its local deterministic validator checks the exact candidate against the active skill structure, evidence states, source classes, replayable calculations, high-tech four-section contract, and humanizer fact lock. A successful candidate receives formal status. A critical contract gap receives one bounded correction opportunity and then a visible draft outcome with diagnostics; advisory gaps do not block formal status. Missing infrastructure produces one terminal failure without automatic retry. When a later skill expands dependencies after content validation, the guard retains the accepted candidate, closes activation first, and performs the exact final-text comparison only after the execution chain is complete.

## Behavior

Compatibility hooks and prompt instructions are not trust boundaries. The production desktop composition must make this package non-removable and keep third-party plugins behind the same tool broker. Receipt producer plugins receive the private `gongchuangPolicy` service only through a host-approved Cordis injection edge; a name match alone cannot mint a receipt.

For a structurally valid numbered-annotation message, task-intent routing and current-user evidence use the comments and current body, not the historical quotations. Asking why a quoted instruction failed does not start that old task again. New instructions in a comment or the body still activate their owning professional task. The model and durable log retain the exact quotations. Invalid annotation metadata remains ordinary text; this projection grants no permission, evidence receipt, or validation exemption.

Task-intent routing excludes explicitly negated actions within their comma-, semicolon-, or sentence-delimited clause. A file-reading request that excludes policy lookup, enterprise materials, or report generation remains ordinary work. Prohibiting source misrepresentation, such as `不能冒充官方政策`, does not request policy research; an eligibility question such as `为什么不能申报` remains actionable. An affirmative professional request in a later clause still activates its owning skill; negation does not grant tool permissions or bypass validation for an active professional task.

A complete clause describing skill responsibilities or prescribing an unknown status when evidence is missing does not request the named business task. An additional affirmative analysis request still activates its own checks; this distinction does not exempt a skill by name or authorize publication.

An explicit request to transcribe existing fields, numbers, or quotations remains a query when it contains no affirmative analysis or artifact-creation action. A policy name or an unverified status in an annotation comment does not independently restart the quoted task. Combining transcription with an actual eligibility judgment still activates professional validation.

A chat calculation explicitly limited by the user to supplied rules, with real policy and eligibility judgments excluded, does not need an official policy source merely because the owning skill depends on policy retrieval. The Host derives this scope from user intent, never the model's task label. Arithmetic, evidence binding and the correction limit remain active; the candidate must disclose its non-eligibility scope and cannot assert entitlement. Direct policy tasks, affirmative eligibility requests and formal artifacts retain official-source requirements. This limited intent classification does not establish semantic correctness of the business conclusion.

A chat comparison explicitly limited to user-provided samples does not require public company or policy sources when peer comparison owns the task. The Host derives this scope from the request; the candidate must disclose its sample-only scope and cannot assert market leadership, market share or eligibility. Actual source binding and arithmetic remain required. Direct policy tasks, formal artifacts and requests for real market conclusions retain their source requirements.

Evidence binding and independent candidate checks report their available diagnostics in the same validation call. Unattested rows may be inspected for arithmetic or structure diagnostics but can never mint a successful receipt. A missing customer-file receipt is distinguished from a fragment mismatch; arbitrary shell output is not accepted as a trusted file read. This avoids consuming the only correction on one error before revealing another, without increasing the correction budget.

Loading the general coordinator or router in an ordinary turn does not itself activate a professional task. The coordinator also owns the shared document reader; its signed operations remain available after real skill activation. An explicit business request or a concrete professional skill still activates the corresponding checks.

When the Client supplies `source.displayText`, task routing uses that existing user-facing projection, excluding attachment reference rows and historical annotation quotes. Product-added reader instructions and attachment filenames cannot independently select a business task. The complete model message and tool authorization remain unchanged; callers without a display projection retain text-based routing.

Tool completion persists delivery checkpoints without appending a user-visible notice between a model tool call and its result. The next pre-step or turn-stop boundary publishes the deduplicated status notice after the tool exchange is complete. This preserves provider message ordering without discarding tool output or changing validation outcomes.

A terminal `draft` or `failed` result rejects the next model step in the same turn. The Host records the issues and retained file references even when no artifact exists, so closing the turn does not depend on the model obeying a tool's stop instruction. Only an explicit user revision in a later turn can reopen a correction opportunity.

When PTC successfully loads a skill, the complete rendered skill instructions are retained through the existing additional-context channel after the root tool result. Curating a short SDK return cannot silently discard the loaded workflow. Direct skill calls already contain this body and do not receive a duplicate copy.

The same pre-dispatch policy rejects direct permanent-deletion commands in Bash and PowerShell, including chained `rm` and `Remove-Item` calls. The refusal directs the model to preserve existing files and create a new authorized path. This limited command check does not interpret arbitrary program effects, encoded commands or shell indirection and is not a replacement for OS confinement.

For long customer documents, professional validation accepts a Host-injected `sourceToolCallId` from a successful `read` or `read_image` call. The Host reuses the captured receipt text as the humanizer fact lock, avoiding lossy model-side document copying while preserving turn attribution and provenance. For static HTML to PDF delivery, chat preflight accepts `candidateArtifactPath`; the Host extracts and validates the real source text, so the model never has to reproduce a long source byte-for-byte. The final PDF still requires a fresh artifact-mode validation and all delivery receipts. Office files remain native OOXML and are not PDF conversion sources.

Every professional validation result includes `nextStep` in its structured return and uses that same text for its tool card. PTC returns the value rather than forwarding the card text. A successful chat-only candidate instructs exact final output; file preflight instructs generation and artifact validation; artifact success instructs the remaining openability, content and branding checks, plus visual inspection for PDF. The result's `formal` status describes professional validation, not completion of file delivery. Search-budget notices preserve this distinction. Existing file identity checks and the single correction opportunity remain unchanged.

The source fact lock applies when humanization owns the current response contract. When humanization is only a quality dependency of a report, application, score, or profile task, the owning professional contract and evidence ledger remain authoritative; the model is not forced to reproduce every token from the underlying customer file.

When the enterprise-panorama skill requires an A/B/C report-mode choice, the Host records that unresolved decision and permits only skill activation plus `ask_user_question` until the user answers. Research and generation cannot use the first or recommended option as an implicit default. A formal Office candidate with a signed `deliveryProfileId` passes chat-mode structural validation before file creation and artifact-mode validation after creation. A skill without its own signed delivery profile receives an explicit instruction to omit that optional ID, not borrow another skill's profile.

## Version lines

The client version is read from `product/gongchuang-client/src/product-version.ts`; the active suite version comes from the Host-verified installed bundle. Documentation examples and test fixtures are not installed-version claims.

Calculation `evidenceIds` reference the evidence array, never other calculation IDs. Derived calculations retain their inputs' original source IDs; rejection explains that distinction without weakening arithmetic or provenance checks. Inline arrow-separated process ordinals and explicitly labelled checklist item limits are layout, while business amounts on the same line still require evidence.

The signed product policy pins the client's bundled baseline. Professional contracts and fixed operations independently bind to the exact active suite version that the Host verified for the current launch, so a separately signed update is not rejected merely because it is newer than the bundled baseline.

```yaml
  config:
    manifestPath: /managed/policy.json
    signaturePath: /managed/policy.sig
    publicKeyPath: /managed/policy.pub.pem
    expectedPublicKeySha256: <64-lowercase-hex-host-anchor>
    expectedProductId: cn.gongchuang.enterprise-assistant
    expectedClientVersion: 0.4.0
    expectedSkillBundleVersion: 1.6.15
    activeSkillBundleVersion: 1.6.15
    professionalContractsPath: /managed/skill-suite/skills/delivery-contracts.json
    skillCallGraphPath: /managed/skill-suite/skills/skill-call-graph.json
    professionalCheckpointDir: /managed/user-data/professional-tasks
```

The public key, its host-pinned SHA-256, both version inputs, and all paths are mandatory. The two professional contract paths must point into the same Host-verified active skill suite, never a user-writable directory. The checkpoint directory must be a Host-owned per-user data directory and must not live inside the active skill suite. No development bypass or unsigned fallback exists in this plugin. The plugin imports the exact V0.4.0 provider registry shared with the product UI and also pins the deny-by-default attribution rule, raw-command denials, required product tools, professional receipt, and four formal-artifact receipt identities, so a valid signature over a weakened manifest is still rejected.

## Model Experience

### Request, tool, and delivery enforcement

#### What the model sees

Allowed providers and tools retain their ordinary content. A denied tool returns the policy reason through the existing tool-result failure path; a provider outside the signed allowlist is rejected before request derivation. One-shot Bash or PowerShell scripts may run inside the product workspace to invoke bundled Python, Node.js, and verified skill scripts; interactive terminals, background jobs, subagents, and workflows remain denied. Browser and computer automation require approval. The signed policy admits final-file publication and the product-owned local-memory tools; neither path bypasses the existing tool broker. A professional task gets one durable notice naming the skill-suite version and required skills. Before presenting a professional result, the model calls `gongchuang_professional_validate` with the exact candidate, evidence ledger, and replayable calculations. The Host binds verified evidence to current-turn trusted reads or source calls, validates the actual artifact text, and reopens a formal file before publication. Critical validation gaps return `repairable` once, then `draft`; infrastructure gaps return terminal `failed`; advisory gaps remain visible without blocking `formal`. Final PDFs still require page-by-page visual receipts from the Host renderer. Formal status remains fail-closed for candidate drift, missing response structure, actionable receipt failure, file drift, user rejection, or more than one final artifact path in one V0.4.0 turn, while the user keeps a marked draft and diagnostics instead of an endless correction loop. The initial professional notice and newly required dependency notice describe the entry point exposed by the current tool catalog. When only `run_code` is exposed, skills, questions, and professional validation use its `tools` object instead of unavailable root tools. An operation rejected for an inactive skill includes the same entry-point guidance. This notice does not change activation, receipt attribution, or repair limits.

##### Late dependency correction

```markdown
If a successful skill activation expands new dependencies after a chat candidate has passed validation, the correction identifies content validation as complete and requests only the missing real skill activations. It does not expose an internal digest, compare the candidate, or repeat the body at that stage. Once activation closes, an exact mismatch may include the retained candidate once. No dependency is marked active without a successful `skill` result, and evidence and candidate identity checks remain unchanged.
```

#### Token effect

Ordinary tasks add no policy tokens. A professional task adds the first-step version-and-skill notice plus one structured local-validation tool call; at most one corrective message follows a repairable result. Late dependency repair carries a short checkpoint instead of the full body, and the same validated body is included in mismatch correction at most once. The deterministic validator itself spends no model tokens, and rejected providers spend no model tokens.

#### KV Cache effect

The policy preserves the existing request prefix for admitted work. A corrective message appends to the same session history, while policy or provider rejection prevents a request instead of replacing cached content.

## Known Limitations and Deferred Work

- PDF.js can deterministically validate only PDFs with a reliable text mapping. A scan-only PDF or one without usable character mappings must use its Office/HTML source, or a future host-constrained OCR content receipt; model-guessed text is never accepted.
- Host evidence attestation proves that declared values, URLs, and digests occur in current-turn user or trusted-tool content; it does not prove that a source is authoritative or that a natural-language claim follows semantically. The active signed suite's source-selection rules, deterministic calculations, conflict disclosures, and human review remain required.
- Office files are generated directly through the signed Python OOXML libraries and never pass through LibreOffice or Office-to-PDF conversion. Only an explicitly requested PDF uses static HTML, Electron Chromium, bundled PyMuPDF inspection and same-source automatic visual regression.
- V0.4.0 validates one formal artifact path per turn. Multiple deliverables require separate turns and independent receipts.
- One-shot Bash or PowerShell execution depends on Host-injected and verified Python and Node.js runtimes. A missing runtime fails explicitly; script execution is never delegated back to the user. Interactive terminals and background commands remain unavailable.
- The desktop host must still prevent alternate unbrokered process, filesystem, browser, and network paths.
- Code signing, notarization, installer upgrade, rollback, and clean-device acceptance are release gates, not implemented by this package.

**Runtime invariant:** No runtime invariant companion is published because signature and identity checks run synchronously before listeners, and an accepted policy is immutable rather than an independently observable relation.
