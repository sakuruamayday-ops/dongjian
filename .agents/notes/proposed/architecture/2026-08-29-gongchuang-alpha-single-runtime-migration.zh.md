# Agent Note: 共创 Alpha 单运行时迁移

Status: proposed

[English](2026-08-29-gongchuang-alpha-single-runtime-migration.md) | 中文

## Problem

共创 V0.3.3 运行在 DeepSeek Harness `dsh-v0.1.1-rc.2` 上，并扩展其 Profile 启动、Remote API、工作区与会话投影、桌面生命周期和产品界面。DeepSeek Harness `dsh-v0.1.2-alpha.1` 替换了其中数项接口。只更新包版本而不迁移产品扩展，会导致客户端无法启动，或静默丢失企业空间、归档与置顶会话、附件、自动任务会话、模型连接或签名运行时策略。把 RC.2 与 Alpha 并存虽然能暂时保留行为，却会让两个运行时同时拥有同一份持久数据和更新生命周期。

## Proposal

V0.4.0 只使用 `dsh-v0.1.2-alpha.1` 作为 Harness 源码和运行时。共创产品服务迁移到 Alpha 的 Profile 组合、Remote 挂载、会话投影、工作区控制器、对话输入和 slot API。产品特有持久字段继续作为 Alpha 工作区与会话接口的显式扩展存在，不再保留第二套客户端运行时。

候选版沿用现有桌面用户数据目录、`persist:gongchuang-v0.1` Electron 分区、凭据存储、企业空间根目录、签名产品策略、签名运行时与技能验签，以及带认证的 loopback 来源。V0.3.3 安装通过既有签名更新事务升级。生产元数据允许选择 V0.4.0 前，升级验证要逐项比较升级前后的账号状态、工作区和会话身份、归档与置顶状态、附件、自动任务绑定、凭据和更新历史。

产品清单同时管理两种身份：`productionBaseline` 继续指向已经发布的 V0.3.3，候选客户端和上游字段则标识 V0.4.0 与准确的 Alpha 提交。运行时请求归因从候选版本唯一来源派生，各连接器不再自行硬编码产品版本。

## Alternatives considered

**等待上游稳定标签并继续停留在 RC.2。** 否决，因为产品决定是跟随每个上游版本，包括 Alpha，并把它作为产品候选进行验证，而不是仅凭预发布状态自动阻塞。

**同时分发 RC.2 与 Alpha。** 否决，因为两套 Profile 启动、客户端运行时或持久化所有者可能对会话投影、凭据、更新和企业空间状态产生不同判断，也会把一次有界迁移变成没有期限的兼容负担。

**在 Alpha 上增加长期 RC.2 兼容层。** 否决，因为当前消费者都能迁移到 Alpha 原生 API。兼容层会保留已经删除的接口，却没有独立消费者或明确移除条件。

## Acceptance criteria

- Host 与 Client TypeScript 聚合只使用一套 Alpha 依赖图完成编译，不再导入 `dsh-client-runtime`。
- 产品测试覆盖 Profile 信任、产品 Remote 挂载、工作区与会话扩展、模型刷新、附件、自动任务、MCP 连接器、签名策略和桌面更新行为。
- 真实 V0.3.3 持久数据的脱敏副本能由 Alpha 存储后端打开并重写，且不丢失任何产品字段。
- 隔离安装的 V0.3.3 客户端能通过客户端内签名更新升级至 V0.4.0 候选，并保留登录状态与产品数据。
- macOS arm64、Rosetta 下的 macOS x64 和 Windows x64 候选制品在生产元数据变更前通过架构、完整性、运行时、技能、文档和生命周期检查。

## Risks

Alpha API 仍可能再次变化，所以下一次上游更新可能需要再次直接迁移。单运行时决定会让这项成本保持可见且有界，但放弃了用兼容外壳推迟迁移的做法。直接更新证据必须来自隔离的打包应用，因为源码测试无法证明应用替换、凭据保留和重启行为。
