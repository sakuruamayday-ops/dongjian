# Agent Note: 文件意图与签名操作发现

Status: proposed

[English](2026-09-03-file-intent-and-operation-discovery.md) | 中文

## 问题

原生测试中的合成 DOC 和 XLS 附件即使带有明确排除语句，仍误入专业流程，随后用六个步骤搜索安装目录中的解析器和操作清单，却没有读取任一文件。直接提供现有操作的准确参数后，同样两次读取可在一个 PTC 程序中完成，原生结果记录的提取耗时分别为 217 毫秒和 345 毫秒，整段答复耗时 20 秒。

意图匹配器没有识别被否定的文件动作，也会漏掉紧贴动作标记之前的否定，并错误地让排除语义跨越逗号。签名操作工具只暴露操作 ID，没有所属技能和参数定义，导致已登记能力难以发现。

## 方案

明确否定只在所在分句内生效，后续分句中的肯定性专业请求仍被保留。现有工具说明和 PTC SDK 应展示已核验清单中的操作、所属技能、用途与参数定义，但不暴露可执行路径，也不新增注册表。PTC 传输、技能激活、签名清单核验、工作区限制、进程隔离和有界失败结果保持不变。

## 备选方案

针对 QA 提示写特例会掩盖普通用户也能触发的问题。关闭专业校验会削弱真实业务流程。要求用户提供工具调用，或允许模型搜索已安装可执行文件，都会保留原有可用性缺陷。

## 验证

最初的定向复现中，15 个所选用例有 13 个失败。修正后的策略、签名运行时和真实 Loader 组合通过 106 项测试，其中包含 PTC 可见操作说明以及肯定与否定两类意图。原生精确调用结果只证明现有解析能力，不证明修复后已经自动正确路由；发布前仍须用普通提示在重建签名客户端中复测。

### 9 月 4 日后续

已安装候选读取混合 PDF 用时 116 秒，并多次把参数定义当成实参、调用不可用的根工具。另一项原生财务计算在通过 PTC 恢复前复现了两次直接 `skill` 调用；计算本身正确，但整轮耗时 82 秒。这两条都是普通消费路径，不只属于附件特例。

签名操作说明改用 JSON 值类型的 `parameterSchema`，区分参数结构与实际参数，并说明 PTC 激活顺序。非字符串的输入输出文件参数会在进程启动前给出具体字段纠正。专业首步通知和后续扩展依赖通知也说明条件性的 PTC 入口。上游传输、激活归属、权限、签名和有界校验行为不变。

三种参数与发现复现修正后均通过，最终策略、操作和真实 Loader 组合测试通过 109 项。首步通知测试需要在合成规则夹具中补入真实财务路由；首次因缺路由失败属于测试夹具缺陷，不是生产路由故障。后续通过的套件使用了修正夹具和更新后的模型可见快照。证据为 V0.4.4 目录下的 `professional-ptc-notice-final.json` 与 `operation-arguments-after.json`。这些源码改动当时尚未安装进运行中的 App，因此不能证明原生延迟已经改善。

### 打包后的原生后续

一个 ASAR 为 `1b777a147ee249fd2bc8866a8aa98ac5f08902d572d68ec0549b52089c024aa0` 的 ARM 候选包含新客户端通知，并保留签名技能 V1.6.16。同一财务提示在 58,780 毫秒内完成，没有根工具或嵌套工具错误；修改前为 82,162 毫秒，并出现两次根工具缺失。两次都正确算出三个比率，单次对比不能形成通用延迟上限。

同一混合 PDF 用时从 116,224 毫秒降至 64,166 毫秒，但仍有一次漏传根 `run_code.description`，并把 OCR 参数猜成 `image`，也没有激活固定提取操作。最终答复还把远程 OCR 错写成无网络处理，把模型检查错写成人工复核。候选技能指引覆盖这些字段和来源区分，但当时尚未签名安装；文字断言不能证明模型遵守。该原生文件流程因此仍只是部分通过。精确合成会话证据为 `native-financial-after-ptc-20260904.json` 和 `native-mixed-after-ptc-20260904.json`。

## 验收标准

普通原生请求无需精确工具说明、解析器搜索或误入专业流程，即可读取上传的合成 DOC 和 XLS，并与签名提取回执一致。肯定性专业请求仍进入现有流程，签名、激活和工作区检查均不得绕过。

## 风险

基于句法的意图匹配器不是通用自然语言解析器。本次只覆盖已观察到的排除语句及直接逗号、分号变体。未签名的技能读取与模板候选分别保留自己的验证和发布证据。
