# Agent Note: 原生验收发现的技能交付指引问题

Status: proposed

[English](2026-09-04-skill-delivery-guidance.md) | 中文

## 问题

B09 的 `enterprise-profile` 任务执行了 28 个步骤，其中猜用了另一个技能拥有的交付画像。现有激活通知只在技能拥有画像时列出画像 ID，没有画像时的静默让模型继续搜索注册表并猜测。B09 的 `evolution-governance` 任务还把“不得发布候选技能”误解为“不得展示用户要求的本地文件卡片”，并把用户提供的事实强化成“缺少审批记录”等结论。

## 方案

激活通知在已登记技能没有签名交付画像时明确说明必须省略 `deliveryProfileId`。本地文件工具的说明区分对话文件卡片、外部上传以及软件或技能发布。两处改动都不改变校验、授权、签名或发布行为。技能候选还会区分用户明确说明不存在的资料与尚未提供的资料，并把部分脚本测试结果保留为部分证据。

桌面端投影在宿主提供 `gongchuang_render_pdf` 时将其设为唯一 PDF 渲染入口，覆盖依赖未解包 Playwright 的独立技能渲染命令，并要求其他可能长驻的命令显式传入 `timeoutMs`。这样 PDF 生成保持在打包应用内，也避免缺少开发依赖后退化为无界浏览器进程。

改写检查器对拉丁标识使用 ASCII 单词边界。Python 的 Unicode 单词边界会把相邻中文视为同一个词，因此可能漏掉 `整机X1`，也可能让只增加空格的格式变化被误判为差异。回归用例覆盖型号变化、缩写变化、中文空格和嵌入的小写标识。

## 备选方案

**让每个技能自行推断交付状态和证据语义。** 真实运行已复现相互冲突的说明、画像猜测，以及超出输入事实的强化结论。

**从业务任务中移除专业校验。** 这会丢弃证据、计算和正式文件检查，并没有修正有界指引与终止行为。

## 验收标准

曾有模型声称 DOCX 的展示来源标签无法绑定 TXT 读取回执。当前实现的直接回归否定了该说法：来源标签不会与文件路径比较，行号也不会阻止逐字子串匹配，但把全角标点改成其他标点确实会失败。用户当时的精确失败仍需结合原始轨迹复核。另一个已确认缺陷是检查点保留了被拒绝的对话候选，却只向用户展示诊断。终止态宿主通知应携带同一轮保留的正文，让现有交付槽在不增加模型步骤、不弱化证据检查、不授予正式状态的前提下展示明确标记且可复制的未验证草稿。

B10 原生业务用例发现了四类问题：流程序号被当成业务数字，计算 ID 被填入来源证据 ID，未知治理记录被改写成缺失，以及订单余额被当成已完成交易。B11 候选增加有界布局回归，通过真实 Loader 向模型说明证据 ID，并修正相应技能指令；一次修复上限和真实数量检查继续保留。人才用例把未提供的任职资料当作“没有任职”，技能中也需明确禁止该推断。能力报告必须保留真实失败调用，技能数量从当前包读取，不能沿用历史常量。

B09 原生轨迹只能证明失败，不能证明后续候选已经修复。回归与后续原生运行分别记录在产品证据中，正式发布状态单独判断。

一次原生财税报告运行已经生成所需 HTML 和结构化事实，但无法从打包应用解析 Playwright，随后直接启动 Chrome 的回退进程持续运行，直到用户停止任务。产品投影与逐步路由提示现在要求所有桌面技能调用已登记的原生渲染器，禁止查找渲染依赖和直接回退外部浏览器，并要求其他具有长驻风险的命令限时执行。单元回归同时覆盖常驻激活通知和逐步提示；只有通过 `gongchuang_render_pdf` 完成真实 PDF 流程后，才能形成原生验收证据。

B10 的投资测算正确区分了已付款新设备、二手设备和后续付款设备，但无条件政策依赖检查拒绝了用户给出的纯计算规则。B12 候选从宿主捕获的用户意图派生这一有限的非资格判断范围，保留全部数字检查并要求候选披露范围。模型任务标签和 QA 标记都不能创造例外。直接政策任务、正式文件和肯定性资格请求继续要求官方来源。单元回归和真实 Loader/PTC 组合同时覆盖允许与拒绝路径，原生验收另行记录。

B12 原生验收到达有限计算检查后，又串行暴露了多个诊断：先出现 shell 读取绑定失败，一次允许修复后才出现缺少派生值。B13 应在证明失败时仍独立计算候选诊断并一次返回两组问题；证明错误仍无条件阻止回执。Loader 回归应在一次后续调用中同时修复绑定与计算问题，并继续执行伪造来源拒绝测试。地方规则管理还要把本地候选目录查询和远程目录匹配分开；曾有原生运行在用户明确仅查本地时转向远程，该轨迹继续作为失败证据。

B12 离线索引测试完成真实写入和版本保留后，因为限制语句 `不能冒充官方政策` 被标记器当成肯定性请求而误入政策校验。修正逻辑应在所在分句中识别明确的来源冒充禁令，同时保留后续分句里的资格问题和肯定性请求。单元与 Loader 回归复现原始误路由；不得增加 QA 标记例外或新的校验次数。

B15 同行对比已经正确比较用户提供的合成数据，但校验器仍在明确“仅样例”请求下要求外部企业和政策来源。B16 候选从宿主捕获的用户意图派生有限对比范围，要求候选做对应披露，并拒绝真实市场或资格断言。正式文件和直接政策工作继续保留来源要求。桌面技能投影还应让明确输入范围优先于工作区格式发现，零参数 SDK 调用必须传空对象，并区分真实审计时间与未提供的业务日期。这些指令不能替代文件系统限制或语义证明，原生违例仍算失败。

B15 的 `skill-authoring` 请求只是描述财务与投资技能职责，并要求未知证据保持未验证，却错误激活了业务校验。意图匹配应排除这些完整描述性分句，同时让新增的肯定性业务请求继续触发检查。真实 Loader 回归同时覆盖两种情况；技能名称和 QA 标记都不提供豁免。B17 还应独立复现生成 Python 在首个缺失行上的失败，并在六种用例、隔离行和排列组合中验证修正副本。技能候选必须要求这些顺序敏感用例，不能把三个方便通过的夹具当成完整脚本验证。

B37 的省级专精特新任务在校验前已激活全部必需技能，却因校验器输入格式没有写入技能文档，连续猜测 JSON、创建探针文件并读取源码，耗时超过五分钟。签名技能应给出完整 JSON 字段和枚举、已签名操作名，并只允许根据完整错误清单修正一次。桌面投影还要明确 `tools.read` 参数、要求在顶层实际等待调用，并把 `run_code` 返回值限制为可无损序列化的 JSON。上述指引覆盖已复现的调用族，不弱化校验器，也不增加重试次数。

## 风险

如果排除条件扩展到超出宿主捕获的用户请求，收窄意图分句可能漏掉真实专业任务。因此候选继续保留直接政策、正式文件、证据、数量和肯定性资格检查，并要求发布前完成最终原生业务流程验收。
