# Agent Note: 产品上游发布审计

Status: implemented

[English](2026-08-24-product-upstream-release-audit.md) | 中文

## 问题

产品从多个 GitHub 项目采用源码或交互决策，但这些关系散落在说明中，发布前可能已经漂移。若把所有活跃参考分支都设为打包阻塞，文档或无关设计变化也会阻止发布；若完全忽略源码底座或路由适配的变化，又可能漏掉适用修复。

## 决策

`product/gongchuang-client/upstream-products.json` 是产品级 GitHub 项目审阅清单。每项记录仓库、跟踪的发行版或分支、已审阅提交、已采用提交、关系和发布策略。每个平台的桌面打包输入检查都会在正式打包前实时查询 GitHub。查询会为整轮审计只解析一次认证：`GITHUB_TOKEN` 优先于 `GH_TOKEN`，本机桌面发布其次复用已登录的 `gh auth token`，只有两者都不存在的机器才使用 GitHub 匿名额度。

精确 DeepSeek Harness 源码底座和已适配的 `dsh-routing-suite` 行为使用 `must-match`：上游移动后必须先审阅并更新清单才能打包。没有随包分发源码的设计参考使用 `report-change`：变化会输出供审阅，但其自身不阻止打包。该审计不自动更新源码，也不替代依赖锁或安全审查。

## 曾考虑的替代方案

**所有参考分支都阻止打包。**不采用，因为仅文档或无关设计参考提交不会改变实际发布代码。

**按周期检查上游。**不采用，因为真正需要作出决定的时点是不可逆的正式打包，普通开发不需要依赖网络检查。

**自动合并最新上游提交。**不采用，因为源码底座升级与方法适配都需要产品兼容性审阅和测试。

## 后果

每次发布都会报告当前上游身份；已分发底座或必需适配基线未经审阅发生移动时，打包会停止。参考项目保持可见，但其活跃分支不会成为普通打包的无关阻塞。GitHub 可用性由此成为发布输入依赖，查询失败必须在打包前解决，不能静默当作当前版本。
