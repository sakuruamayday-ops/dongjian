# Agent Note: 按需场景评估与项目状态对账

Status: implemented

[English](2026-08-26-scenario-evaluation-and-state-reconciliation.md) | 中文

## Problem

仓库已经具备确定性单元测试、属性测试、快照、浏览器测试、真实 API 测试、打包测试和设备测试，但“全面测试 agent”这类要求仍可能演变成一组没有稳定场景身份、停止条件，也不区分探索性判断与回归证据的无界模型对话。外部对话模拟器能够生成有价值的用户变化，但把它的 Python 与 LangChain 依赖图加入产品，会重复现有测试基础设施并扩大产品或贡献者运行环境，却不能证明测试实际经过组装后的 DSH 应用。

发布工作还会同时改变产品清单、`CONTEXT.md`、产品文档、不可变回执、测试与 Agent Note 中的事实。只更新开头的版本段落而不对账后面的当前状态文本，会让同一文档同时声称两个生产版本。引入通用项目状态目录，则会在现有事实归属文件之外再造一个权威来源。

## Decision

Agent 行为评估采用按需、场景驱动的工作流。每个场景记录用户目标、合成前置数据、相关轮次、必须和禁止出现的可观察行为、最大轮次、费用上限、模型身份、终止条件及证据位置。最窄的确定性仓库测试仍是主要回归证据。真实提供方运行仍由人工明确请求；LLM 评判在发现被产品自有断言或校验器复现前，只作为探索结果。

[Plurai IntellAgent](https://github.com/plurai-ai/intellagent) 是外部评估辅助工具，不是产品依赖，也不是强制开发依赖。外部运行固定已经审阅的 commit，关闭 Plurai 遥测，只使用合成或不可逆脱敏数据，并显式设置费用和轮次上限。测试替身或兼容 LangGraph 的 agent 只能证明 IntellAgent 评估器能够运行；对产品作出判断，必须由持续维护的适配器进入组装后的 DSH 应用。GUI、原生集成、签名、更新和性能继续使用各自所属测试。

项目状态对账同样按需执行，在发布、长时间实现、分支集成或审查使持久事实可能变化时使用。它吸收 [Project State Governor](https://github.com/Ghost011118/project-state-governor) 的语义差异生命周期，同时保留本仓库现有权威来源：机器可读产品身份和不可变回执负责已发布事实，`CONTEXT.md` 负责当前跨模块术语，中文产品文档负责产品范围和证据，活跃 Agent Note 负责设计理由，代码与测试负责已实现行为。该流程不创建 `PROJECT_STATE.md`、`.project/`、状态档案或新 CI 门禁。

状态对账区分当前断言与历史发布记录，按证据实际支持的层级核验完成状态，并只修改最小所属文件。已归档 Agent Note 保持冻结。已实现 Agent Note 维持当前状态，或通过现有三文件归档流程移动。对话时间线、未核实的审查意见和临时调试猜测不会成为持久状态。

## Verification

IntellAgent commit `4125d1c18ec351655b2e37df5d396d08eaa4fa60` 在隔离的 Python 3.12 环境中完成安装，并在关闭遥测后通过 60 项上游测试；运行同时出现 8 条 Pydantic v2 弃用警告。另一项使用 monkey patch 的检查确认，设置 `PLURAI_DO_NOT_TRACK=true` 后不会发起分析 HTTP 调用。这些结果只证明本次评估涉及的上游测试路径可运行，不证明 IntellAgent 已覆盖 DSH 产品。

Project State Governor commit `9cae9694bc9c5042ba515b9d971e640f71c382c3` 通过 Codex skill 结构校验。把它的对账方法用于 V0.3.1 仓库后发现：尽管 `product-manifest.json`、release_id 14 和 V0.3.1 不可变回执已经一致，部分当前状态文本仍把 V0.2.9 或 V0.3.0 写成生产版。修正这些既有归属文件，证明语义差异方法能够产生实际价值，而无需再建状态文件。

两个适配后的 skill 均通过 Codex skill 结构校验；本记录和修正后的当前状态文本则由仓库现有检查覆盖。两个外部项目都不会提供或替代仓库的产品测试。

## Alternatives considered

**把 IntellAgent vendoring 到仓库或客户端运行时。** 不采用，因为它体量较大的固定 Python 依赖图、外部模型费用、默认遥测和面向 LangGraph 的聊天机器人接口，都不能取代现有组装产品测试路径。

**把 LLM 评判分数作为发布门禁。** 不采用，因为模型判断具有非确定性；它可以帮助发现问题，却不能成为协议、安全、版本身份或精确可见行为的权威证据。

**采用 Project State Governor 默认的 `PROJECT_STATE.md` 或分层 `.project/` 布局。** 不采用，因为 `CONTEXT.md`、产品元数据、产品文档、回执和 Agent Note 已经有明确归属。第二棵状态目录只会转移冲突，不能解决冲突。

**每项变更都运行两套工作流。** 不采用，因为本地可逆变更已有定向测试和 Git 历史。只有附加证据能够回答一个具体不确定性时，才运行场景评估或状态对账。

## Consequences

今后的广泛 Agent 评估会拥有有界场景，以及从探索性发现进入确定性回归覆盖的明确路径。外部模拟器依赖和客户数据留在产品之外；以后如果真实评估需求足以支撑维护成本，仍可增加适配器。

发布和长任务的状态更新会先比较现有权威来源再写入。当持久事实变化时，这增加了一个明确的对账步骤，但不增加新的正典文件或强制门禁。流程也可以报告没有发生语义状态变化，这优于制造文档改动。
