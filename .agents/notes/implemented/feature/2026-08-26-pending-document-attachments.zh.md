# Agent Note: 待发送文档附件

Status: implemented

[English](2026-08-26-pending-document-attachments.md) | 中文

## 问题

文档导入最初把所选文件编码为可见的生成说明文字。这会把用户正文与附件生命周期耦合，让简单的移除操作依赖文本解析，也让文件卡无法安全打开受控工作区副本。

## 决策

产品在输入框之外持有逐会话的待发送文档状态。导入只把受控相对引用加入该状态，不修改输入文字，也不发送任务。每个会话使用独立的浏览器存储键持久化脱敏引用，新产品运行时只恢复有界且位于受控导入目录的记录。提示词准备层只在用户实际提交任务时附加引用，发送成功后消费引用，发送失败则保留。迁移解析器会从旧草稿移除生成的附件块，并把其中引用恢复到同一状态。

对话外壳通过输入框内部的 `conversation.input.dock` 渲染紧凑文件卡，位置在图片附件与可编辑文字上方。每张卡片包含两个相互独立的操作。点击卡片主体时，桌面 Host 只有在确认相对路径解析为受控导入目录内的普通且非符号链接文件后，才打开导入副本。关闭控件只移除该会话的待发送引用，绝不删除、移动或改写源文件、导入副本、企业记录及其他会话引用。输入框不在普通编辑阶段时，移除操作保持禁用；图片附件继续使用既有浏览器插槽和生命周期。

发送成功只消费本次已准备的文档对象。更晚完成的导入，或删除后重新加入的同一路径引用，会保留到下一份草稿。发送结束不会重新创建已经删除会话的浏览器存储项。混合拖入会把受支持图片和文档分开：输入框左侧位置接收常驻输入框的图片接收回调和锁，因此图片限制、预览和视觉提交仍由上游所有。宿主会在持久文件名长度上限内为重名后缀预留空间，路径限制测试能够区分父目录段 `..` 与合法的点开头文件名，同时继续拒绝穿越和符号链接。

## 考虑过的替代方案

**继续把生成引用写入可见草稿。** 不采用，因为展示、用户正文和附件生命周期仍会耦合，普通编辑也可能静默改变文件引用。

**打开渲染器提供的绝对路径。** 不采用，因为不可信渲染器不能选择任意本机文件。Host 必须从当前工作区和受控相对引用派生并校验路径。

**关闭卡片时删除导入副本。** 不采用，因为关闭表示“本次待发送消息不再引用该文件”，不表示删除文件。

**把文档卡片显示在输入框上方。** 不采用，因为卡片属于待发送消息，工作流状态和用量读数仍应位于输入框外部。

## 影响

输入框不再出现生成的附件说明或重复提示。待发送文件卡可以跨应用重启或更新恢复，而损坏的已存路径无法进入面向模型的提示词准备。用户可以在发送前打开所选文件确认内容，也可以解除引用，同时 Host 始终持有路径权限。组件、提示词准备、桌面导入、preload 打包和窗口生命周期测试覆盖恢复、两项操作及其失败行为。
