# Agent Note: 共创 macOS 服务器自管更新

Status: implemented

[English](2026-08-20-gongchuang-self-managed-macos-updates.md) | 中文

## Problem

macOS 产品通过共创服务器分发，并使用 ad-hoc 代码完整性，而非 Apple Developer ID 身份。Squirrel.Mac 与普通 Electron 更新通道依赖已安装应用和替换应用之间稳定的 Apple 签名要求，因此不能对这些版本完成身份验证与安全替换。若把 HTTPS 压缩包或下载页展示的校验和直接视为权威，更新源一旦被入侵，也能在不受已安装 Host 固定身份约束的情况下选择可执行代码。

V0.2.3 至 V0.2.5 客户端把暂存运行时索引绑定到验签进程编译时的客户端版本。即使新应用的服务器清单、压缩包、代码完整性、运行时签名与技能签名全部有效，只要版本正确地高于旧客户端，也会在辅助进程接管前失败。已经安装的这些二进制无法通过损坏路径取得修正后的更新器，而原隔离演练运行的是目标版本源码，不是已发布源版本二进制。

## Decision

受影响的安装需要使用一次门户 DMG。用户选择准确的 Apple 芯片或 Intel 安装包，替换 `/Applications` 中的应用，并通过门户的一键复制或手动选取后粘贴方式执行 `xattr -dr com.apple.quarantine "/Applications/共创企业助手.app" && open "/Applications/共创企业助手.app"`。该命令只移除这个具名应用的隔离属性并将其打开，不是通用 Gatekeeper 绕过。V0.2.6 及后续版本使用下述已修正的客户端内认证更新器。

打包 Host 固定产品运行时 Ed25519 公钥指纹和正式签名层级。[`MacSelfUpdaterController`](../../../../apps/desktop/src/macos-self-updater.ts)从同一个无凭据 HTTPS 位置获取 `desktop-release-index.json` 及其分离式 `.sig`，并禁止重定向。它先验证 JSON 原始字节，再接受产品 id、语义版本、源码提交、发布时间、分架构压缩包身份、字节数、SHA-256 摘要，以及内置运行时与技能索引摘要。发布操作通过 [`build-signed-macos-update-manifest.ts`](../../../../apps/desktop/scripts/build-signed-macos-update-manifest.ts)同时生成并签署两个架构记录；先发布签名、后发布清单，使并发读取到的不完整更新保持快速失败。

## 已签名应用验证

更新器把选定压缩包以流式方式写入每个事务的私有目录，解压前拒绝任何字节数或 SHA-256 不一致。解压后的 ZIP 只能包含一个 `共创企业助手.app`，符号链接不得逃逸应用目录树。验证器检查 Bundle ID、版本、可执行文件名称、唯一且准确的 `arm64` 或 `x86_64` 架构，以及 `codesign --verify --deep --strict` ad-hoc 完整性；随后根据清单认证的目标版本验证内置产品运行时，不再使用旧验签进程版本，并根据固定发布者指纹和正式层级独立验证已签名技能套件。两个已验证索引摘要必须等于清单值。服务器签名、压缩包摘要、应用身份、目标运行时身份、运行时签名与技能签名是相互独立的检查，任何单个校验和都不能替代其他检查。

## 安装事务

全部验证通过后，更新器把暂存应用复制到当前安装旁边，证明应用所在卷支持 Foundation 安全替换，并记录父进程的可执行路径和启动时间。随后更新器先关闭桌面运行时，再启动分离式 [`macos-update-helper`](../../../../apps/desktop/src/macos-update-helper.ts)，并等待该精确 helper 进程写入 waiting 回执后完成交接。helper 初始化失败时，客户端会先终止并等待该 helper 退出，再报告失败。辅助进程只在已记录的父进程身份仍存在时等待，通过 `NSFileManager` 安全替换把已验证暂存应用放到规范路径，同时把旧应用保留到事务专用 previous 路径，并在启动环境中携带事务 id 打开替换应用。helper 自身以 Electron Node 模式运行，因此调用 Launch Services 前会删除 `ELECTRON_RUN_AS_NODE` 和 `GONGCHUANG_UPDATE_HELPER`，同时保留无关变量。新进程先取得单实例锁，再记录自身可执行路径和进程启动时间，供存活判断与终止操作复核，并在提交前强制执行与打包验收相同的完整产品界面探针。

由 V0.4.0 创建的安装任务使用 schema 2。更新器会在运行时关闭前证明事务目录支持同目录 hard link。提交方和恢复方分别预写完整、不可变的决策候选，再通过禁止覆盖的 hard link 发布；只有一个进程能够胜出，普通状态文件只作为诊断投影。恢复方必须先赢得决策，之后才允许停止进程或替换应用，并用同一个 Foundation 操作反向恢复，因此安装与恢复期间规范应用路径始终存在。替换应用启动失败时会原子取得 restoring 决策并启动恢复 helper；首次 helper 已退出时，后续替换应用启动会再次完成该交接。即使诊断状态无法写入，committed 和 restoring 决策仍保持权威。helper 在 waiting 回执后、应用替换前退出时，只有旧产品真实启动完成且已记录的 helper 身份消失，事务才会被对账为 failed。事务专用 previous、failed、staged 和 staging 路径只在最终选定的应用达到 ready 后移入废纸篓。V0.3.3 创建的 schema 1 任务继续使用已发布 helper 能理解的旧状态文件，所以 V0.3.3 到 V0.4.0 必须由精确的已发布源包验收，不能从 schema 2 测试外推。

## Alternatives considered

**Apple Developer ID、公证与 Squirrel.Mac。** 本分发方式不采用，因为产品明确使用不依赖 Apple 开发者身份的共创服务器路径。未来如采用该通道，需要另行评审签名与迁移决定，不能通过弱化 Squirrel 签名检查来模拟。

**只信任下载页、TLS 或公开的 SHA-256 值。** 不采用，因为这些机制不会在已安装 Host 内固定可执行文件发布者。分离式 Ed25519 签名对清单进行身份验证，摘要则把选定压缩包绑定到该认证记录。

**继续发布普通清单并从 V0.2.3 或 V0.2.5 重试。** 不采用，因为新产物无法改变旧进程编译后的版本比较。伪造目标运行时版本或提供双运行时会弱化发布身份；门户 DMG 是进入已修正更新器的一次性明确恢复路径。

**提供回滚到 V0.1.1 或保留多个已安装版本。** 不采用，因为这会引入另一种产品状态，并可能恢复使用旧策略、运行时和技能假设的应用。辅助进程只保留恢复替换启动失败所需的更新前副本。

## Consequences

受影响的 mac 用户需要完成一次手工覆盖，之后才能使用已修正的认证更新。V0.2.6 及后续每次更新都要求服务器 JSON、分离式签名、对应架构压缩包、目标客户端版本和两棵内置签名树一致；缺少架构、签名无效、发生重定向、体积不符、压缩包被修改、应用身份错误、helper 模式环境泄漏或启动不完整时，都不会接受候选，而是保留或恢复当前可用安装。发布验收必须让实际打包的源应用通过自身 UI 更新 IPC 执行已签名目标更新；使用目标版本源码构造控制器或模拟 launch 回调都不能作为充分证据。

更新通道与 Apple 公证相互独立，也不会全局关闭 Gatekeeper。其信任基础是保护外置 Ed25519 签名私钥、在 Host 中保留固定公钥身份、原子发布已签名清单对及其引用压缩包，并保持服务器路径仅使用 HTTPS。事务恢复会在安装期间占用临时磁盘空间，并以放弃用户主动降级换取唯一且确定的当前版本状态。

正式包验收使用实际已发布的源版本二进制和隔离用户数据根，先创建原生 `safeStorage` 密文，再写入活动、归档、删除和置顶的企业空间与会话、附件对象、自定义模型连接、停用的已安装社区技能、企业分区长期记忆和停用的自动化任务。验收证明已签名目标版本重启后能够解密或读取同一状态。第二个隔离事务在启动提交前只终止 helper 记录的目标 PID，并证明源应用恢复启动后仍读取同一状态。该验收绝不读取正式安装应用的用户数据。
