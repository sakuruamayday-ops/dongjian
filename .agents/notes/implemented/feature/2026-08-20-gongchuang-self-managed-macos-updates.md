# Agent Note: Gongchuang self-managed macOS updates

Status: implemented

English | [中文](2026-08-20-gongchuang-self-managed-macos-updates.zh.md)

## Problem

The macOS product is distributed from the Gongchuang server with ad-hoc code integrity rather than an Apple Developer ID identity. Squirrel.Mac and the ordinary Electron update channel rely on a stable Apple signing requirement across the installed and replacement applications, so they cannot authenticate or safely replace these releases. Treating an HTTPS archive or a checksum displayed on a download page as authority would also let a compromised feed choose executable code without an identity pinned by the installed Host.

The V0.2.3 through V0.2.5 clients bind a staged runtime index to the verifier process's compiled client version. A correctly versioned newer application therefore fails before helper handoff even when its server manifest, archive, code integrity, runtime signature, and skill signature are valid. Those already-installed binaries cannot acquire a corrected updater through the broken path, and the original isolated drill used target-version source rather than the released source binary.

## Decision

An affected installation uses the portal DMG once. The user selects the exact Apple silicon or Intel package, replaces the application in `/Applications`, and uses the portal's copy action or manual-selection fallback for `xattr -dr com.apple.quarantine "/Applications/共创企业助手.app" && open "/Applications/共创企业助手.app"`. The command removes quarantine only from that named application and opens it; it is not a general Gatekeeper bypass. V0.2.6 and later releases use the corrected authenticated in-client updater described below.

The packaged Host pins the product-runtime Ed25519 public-key fingerprint and formal signing tier. [`MacSelfUpdaterController`](../../../../apps/desktop/src/macos-self-updater.ts) fetches `desktop-release-index.json` and its detached `.sig` from the same credential-free HTTPS location with redirects disabled. It verifies the exact JSON bytes before accepting the product id, semantic version, source commit, publication time, architecture-specific archive identity, byte size, SHA-256 digest, and embedded runtime and skill index digests. A release operation generates and signs both architecture records together through [`build-signed-macos-update-manifest.ts`](../../../../apps/desktop/scripts/build-signed-macos-update-manifest.ts); publishing the signature before the manifest makes a concurrent partial update fail closed.

## Signed application verification

The updater streams the selected archive into a private per-transaction directory and rejects any byte count or SHA-256 mismatch before extraction. The extracted ZIP contains exactly one `共创企业助手.app`; symbolic links cannot escape that application tree. The verifier checks the bundle id, version, executable name, one exact `arm64` or `x86_64` architecture, and `codesign --verify --deep --strict` ad-hoc integrity. It then verifies the embedded product runtime against the target version authenticated by the manifest, not the old verifier process version, and independently verifies the signed skill suite against its pinned publisher fingerprint and formal tier. Both verified index digests must equal the manifest values. The server signature, archive digest, application identity, target runtime identity, runtime signature, and skill signature are separate checks; no single checksum substitutes for the others.

## Installation transaction

After all verification succeeds, the updater copies the staged application beside the current installation, proves that the application volume supports Foundation safe replacement, and records the parent process executable and start time. It then shuts down the desktop runtime, starts the detached [`macos-update-helper`](../../../../apps/desktop/src/macos-update-helper.ts), and waits for that exact helper process to record its waiting receipt before completing the handoff. A helper initialization failure kills and reaps that helper before the parent application reports failure. The helper waits only while the recorded parent identity still exists, uses `NSFileManager` safe replacement to put the verified staged application at the canonical path while retaining the old application at the transaction-specific previous path, and opens the replacement with the transaction id in the launch environment. The helper itself runs Electron in Node mode, so its Launch Services call removes `ELECTRON_RUN_AS_NODE` and `GONGCHUANG_UPDATE_HELPER` from the child environment while retaining unrelated variables. The new process obtains the single-instance lock, records its executable and process start time for liveness and stop operations, and requires the complete product-UI probe used by packaged acceptance before commit.

V0.4.0-created install jobs use schema 2. The updater proves the transaction directory supports same-directory hard links before runtime shutdown. Commit and restore each publish one fully written immutable decision candidate through a no-overwrite hard link; only one process can win, and the ordinary state file is a diagnostic projection. Restore wins before it stops or replaces anything and uses the same Foundation operation in reverse, so the canonical application path remains present during both installation and recovery. A replacement that fails startup atomically claims restoring and starts a recovery helper; a later replacement launch repeats that handoff when the first helper has died. Committed and restoring decisions remain authoritative when their state projections are unwritable. A helper that dies after its waiting receipt but before replacement is reconciled to failed only after the old product reaches ready and the recorded helper identity is absent. Transaction-specific previous, failed, staged, and staging paths move to Trash only after the selected application reaches ready. V0.3.3-created schema 1 jobs retain the legacy state-file commit understood by the already released helper; the V0.3.3-to-V0.4.0 path therefore requires exact packaged-source acceptance rather than an inference from schema 2 tests.

## Alternatives considered

**Apple Developer ID, notarization, and Squirrel.Mac.** Rejected for this distribution because the product deliberately uses the Gongchuang server path without an Apple developer identity. Adopting that channel later requires a separately reviewed signing and migration decision; it is not emulated by weakening Squirrel's signature checks.

**Trust the download page, TLS, or a published SHA-256 value alone.** Rejected because those mechanisms do not pin the executable publisher inside the installed Host. The detached Ed25519 signature authenticates the manifest, while the digest binds the selected archive to that authenticated record.

**Publish another normal manifest and retry from V0.2.3 or V0.2.5.** Rejected because a newer artifact cannot change the old process's compiled version comparison. Falsifying the target runtime version or shipping a dual runtime would weaken release identity; the portal DMG is the explicit one-time recovery into the corrected updater.

**Expose rollback to V0.1.1 or keep multiple installed versions.** Rejected because it creates another product state and can restore an application with older policy, runtime, and skill assumptions. The helper retains only the update-time copy required to recover from a failed replacement startup.

## Consequences

Affected Mac users perform one manual replacement before corrected authenticated updates become available. Every V0.2.6-or-later update requires the server JSON, detached signature, architecture archive, target client version, and both embedded signed trees to agree; a missing architecture, invalid signature, redirect, size mismatch, modified archive, wrong application identity, helper-mode environment leak, or incomplete startup preserves or restores the current working installation instead of accepting the candidate. Release acceptance must execute the actual packaged source application through its UI update IPC against the signed target; a controller constructed from target-version source or a mocked launch callback is not sufficient evidence.

The update channel remains independent of Apple notarization and does not suppress Gatekeeper globally. Its trust rests on protecting the external Ed25519 signing key, retaining the pinned public identity in the Host, atomically publishing the signed manifest pair and referenced archives, and keeping the server path HTTPS-only. Transaction recovery occupies temporary disk space during installation and gives up user-directed downgrades in exchange for one deterministic current-version state.

The packaged release acceptance starts the exact released source binary with an isolated user-data root, creates native `safeStorage` ciphertext, and then stages persisted active, archived, deleted, and pinned workspaces and Sessions, an attachment object, a custom model connection, a disabled installed community skill, an enterprise memory partition, and a disabled automation. It proves the signed target can restart and decrypt or read the same state. A second isolated transaction terminates only the helper-recorded target PID before startup commit and proves that the source application restarts with the same state. This acceptance never reads the installed application's user data.
