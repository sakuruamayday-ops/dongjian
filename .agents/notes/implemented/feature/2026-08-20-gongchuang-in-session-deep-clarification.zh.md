# Agent Note: 共创会话内深度澄清

Status: implemented

[English](2026-08-20-gongchuang-in-session-deep-clarification.md) | 中文

## Problem

复杂企业任务常在用户与助手尚未就目标、范围、依赖、风险和验收标准形成共识时，就进入文件修改或正式交付。直接暴露上游开发者工作流名称，会让这种工作纪律只对技术用户可理解；另建向导或隐藏的访谈记录，则会把一个任务拆进两套历史，并产生 Session 领域并不拥有的恢复语义。

## Decision

共创企业助手将该能力呈现为`深度澄清`。带有 tooltip 且支持键盘操作的按钮占用现有对话输入工具栏，不新增侧栏页面、窗口或产品级工作流存储。用户选择该按钮后，客户端只为当前 Session 开启一次性待命状态，不创建空白会话轮次，也不修改或提交当前草稿。用户下一次真正发送非空任务时，普通发送链才会把简短显式启动语句与任务原文合并为一条消息。按依赖分轮、推荐答案格式、事实核验分工、共同理解清单和确认前工作流约束全部由签名技能负责，客户端不复制完整技能内容，从而避免两个真相源。

一次性待命状态按 Session 保存在客户端中，由普通输入发送链按事务结果结算。只有 Host 接受准备后的消息才关闭待命状态；拒绝或传输失败时，用户草稿和待命状态都会保留，方便直接重试。真实任务送出后，请求与每次回答都是普通对话消息，因此 Session 历史是唯一持久访谈记录；既有刷新、重启、回放和恢复路径可以保留整个访谈，无需另一种持久化格式。

只有同一 Session 已经包含五次用户提问，且用户正在编写高置信度正式交付物、多动作任务或范围存在实质歧义时，草稿分类才可以显示一次可选建议。建议提供`为下一条消息启用`和`直接继续`，自身绝不提交或阻塞草稿。浮层第一次可见时，客户端就在用户选择操作前把本会话建议记为已消费，因此关闭、接受、拒绝、重新挂载或重启都不会在该 Session 中再次显示。这个本地小回执不保存访谈内容，也不形成第二套工作流状态；真正启动后的澄清仍只保存在对话历史中。问候、普通问题、礼貌问句、只提到删除或发送等危险动作的疑问、短改写、检索和局部可逆修复不会触发建议。

用户可见文案不出现上游工程技能名称或内部调度术语。产品包拥有中文入口、一次性待命状态、建议与拒绝状态和呈现；签名技能禁止隐式调用并独占完整工作流；通用对话包继续拥有消息准入与持久历史。共同理解确认属于工作流约束，既有 Host 硬确认仍只用于发布、提交、发送和删除等高影响边界。

技能同时负责显式收敛。用户可以在任一轮选择`按推荐继续`、`跳过澄清`或`取消任务`。推荐答案只能代替用户确定可逆、低影响选择，高影响选择继续要求明确确认。只有确认或排除决策分支，或者已核验事实解锁新分支，才算本轮取得进展；连续两轮没有这类进展时，技能停止重复同一组问题，只提供一次采用安全推荐默认值、跳过澄清或取消任务的紧凑选择。工具或外部条件不可用时，只阻塞依赖它的分支，不重复调用同一不可达能力。

## Alternatives considered

**启发式判断命中后强制澄清。** 不采用，因为分类器无法充分判断用户的紧迫程度和真实意图，不足以阻断普通工作。分类结果只提供选择。

**增加独立访谈向导和持久决策树记录。** 不采用，因为这会复制 Session 历史，需要独立的重启与迁移行为，还会迫使用户离开后续执行任务所在的对话。

**直接暴露上游技能名称与控件。** 不采用，因为其中包含开发者概念和更广泛的工程文档行为，不属于企业助手。产品保留其提问纪律，但只呈现业务能力。

**只依赖自动识别。** 不采用，因为短而高风险的请求也可能需要澄清，词法分类器无法可靠识别。每个可用 Session 都保留显式工具栏入口。

## Verification

组件测试覆盖键盘焦点与 tooltip、空输入点击只待命不发送、取消待命、同一会话前五次提问不提示、达到阈值后只显示一次、重建模式后仍保持已消费，以及正式交付、多步骤、歧义任务和普通任务负例。输入服务测试验证下一条真实任务在不改动可见草稿的前提下被包装，成功后关闭待命、失败后保留待命。技能测试验证禁止隐式调用、主动结束选项始终存在、连续两轮无进展后禁止第三轮重复问题、不可达能力不重试，且完整流程仍由签名技能持有。类型检查与类型感知 lint 覆盖对话包、产品包及变更组件。

## Consequences

用户可以在尚未输入任务时先准备一个审慎决策阶段，不会产生没有任务原文的无意义空轮次；完整访谈也会随对话历史一同保留。建议分类器有意保持保守，可能漏掉复杂任务；延迟到五次既有提问后才建议，并在第一次显示时永久消费，可以避免反复打扰，而显式入口始终可用。只要每轮确实解决了依赖，访谈可以超过两轮，但不能无限重复没有变化的问题集合。发送前待命标记刻意只是客户端瞬时状态；按 Session 保存的建议回执不含任务内容，两者都不形成第二套工作流记录。只有真实任务进入 Session 后，持久化工作流才开始。
