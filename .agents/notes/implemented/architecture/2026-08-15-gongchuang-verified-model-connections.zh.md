# Agent Note: 共创已验证模型连接

Status: implemented

[English](2026-08-15-gongchuang-verified-model-connections.md) | 中文

下文中的逐模型选择探针、验证缓存和选择器技术状态展示，已被[无探针模型选择](../simplification/2026-08-23-gongchuang-model-selection-without-probes.zh.md)部分替代。配置阶段的凭据验证、已鉴权目录发现、事务式持久化、适配器采用和系统凭据库边界继续有效。

## 问题

共创企业助手向不需要理解 Cordis 组合、凭据引用或 pi-ai profile 的普通用户提供 DeepSeek、OpenCode Go、硅基流动和 Orgarid 三个中转站，以及一条自定义 API 路由。表单在点击后直接显示完成，无法证明密钥已经通过鉴权、服务商返回了可用模型，也无法证明已挂载适配器能真正调用该模型。静态适配器目录还会在中转站新增、改名或删除模型时，让连接回执与模型选择器不一致。先持久化、后发现失败会留下错误凭据和只写了一半的自定义 profile。本产品需要一份统一的设置与发现契约，明确区分已输入、已保存、已鉴权、当前目录已发布和已通过对话验证。

## 决策

私有 Host 服务 `@gongchuang/model-connections` 负责五条产品路由：`deepseek-official`、`opencode-go`、`siliconflow`、`orgarid` 与 `custom-api`。renderer 只通过一次 Remote 调用提交刚刚输入的密钥，永远不会收到已保存密钥或凭据引用。Host 使用带鉴权的 `/models` 请求验证密钥，拒绝重定向，把响应限制在 4 MB，并在 20 秒后超时；自定义端点只允许 HTTPS，或采用 HTTP 的本机回环地址。

DeepSeek 和三个受管中转站会用已鉴权端点目录替换各自的适配器目录，然后要求已挂载适配器报告每一个已采用的精确模型 ID。Host 从可用目录中选择产品偏好模型，将密钥写入 `@gongchuang/credentials-keychain`，并只发布包含阶段、路由、验证时间、可用模型数量、所选模型、已验证精确模型 ID 和可理解消息的脱敏回执。启动协调、打开选择器、网络恢复和明确刷新都使用这一份投影。DeepSeek 使用 `llm-deepseek`，可与中转站组并行刷新；共用 `llm-pi-ai` 的提供方按同一设置版本序列提交，避免“全部刷新”把同批其他提供方的写入变成过期修改。目录未变时保留精确模型验证；凭据、端点、适配器、能力或模型成员身份变化时，对应结果失效。

自定义路由采用事务式处理。Host 先探测端点、选择其公布的模型，再以随机凭据引用写入密钥、提交一份 `llm-pi-ai` profile，并验证 `ctx.llm` 确实注册了 `custom-api`。端点对 `/models` 返回 404、405 或 501 时，可将用户明确输入的一个模型 ID 登记为纯文本候选；没有 ID 仍然报错。任何失败都会恢复上一份 profile，并移除未使用的候选密钥。如果并发设置变更使回滚不再安全，Host 会把候选保留在 OS 凭据库中并明确报告该状态，而不是删除一条并发 profile 可能已经引用的密钥。

选择器将每个精确模型行标记为已验证或待验证，并从适配器元数据独立显示文本、图片、推理和提供方文件能力。选择待验证模型时，先显示明确的额度确认；然后 Host 使用固定非敏感提示词 `只回复 OK`，最多生成一个输出令牌并在 30 秒后超时。取消时不发请求。成功后只将当前连接身份下的精确模型提升为已验证；失败不改变会话模型。成功目录删除当前模型时，下一次发送前要求用户替换；瞬时目录失败会清空可选行，不会把缓存目录冒充为当前目录。

模型面板底部常驻一个明确刷新命令。刷新期间按钮禁用、现有刷新图标旋转、菜单保持打开，并更新当前会话的共享目录。该交互参考 Hermes Agent `ModelMenuPanel` 的作用域刷新方式，但明确不采用 Hermes 的旧目录失败降级，因为共创产品要求刷新失败后清空可选行。

桌面组合会在 Cordis 挂载之前固定官方适配器身份。Host admission 必须看到 `@deepseek-ai/dsh-llm-deepseek`、精确的 `OPENCODE_API_KEY` 绑定、`@gongchuang/model-connections`，以及初始模型 `deepseek-official` / `deepseek-v4-flash`。组合层只要出现 DeepSeek 端点、OpenCode 提供方多出字段、缺少必需行或插件被替换，就会拒绝启动。运行期自定义路由仍然是 settings 服务中的数据，而不是与宿主同进程的社区 Cordis 插件。

本决策在共创桌面产品范围内具体化了[通用凭据边界](2026-07-30-credential-boundaries-and-atomic-registration.zh.md)，不会改变 `credentials-local` 或通用 DSH Models 页面。

## 曾考虑的替代方案

**把表单提交成功当作配置完成。**不予采用，因为这会重现产品界面正要消除的假完成状态。

**先保存密钥再探测。**不予采用，因为无效密钥会成为持久状态，自定义 profile 写入还可能留下不可用路由。

**只信任 `/models`，不检查已挂载适配器。**不予采用，因为 profile 更新可能没有抵达已挂载适配器。服务更新动态目录后，仍会在发布就绪状态前验证每个精确 ID 已被采用。

**配置时发送一次可能计费的对话请求。**不予采用，因为模型目录鉴权足以验证凭据。独立的首次选择请求只在用户确认某个精确待验证模型后发生，且输出上限为一个令牌。

**刷新失败后继续让旧模型目录可选。**不予采用，因为在无法排除删除或改名的时候，缓存行会被误解为当前状态。瞬时故障后已验证当前模型可以继续尝试，但旧行不作为新鲜候选显示。

**通过共创账号服务器代理提供方凭据。**V0.1 不采用，因为桌面端与跨设备产品数据同步并不依赖该设计，却会让服务器成为模型机密的托管方。

## 后果

模型选择器会区分已安装适配器、已鉴权目录、待验证精确模型、已验证精确模型、目录暂不可用和已下线模型。失败或不兼容端点继续明确显示为不可用；只有 Host 回执表明凭据或自定义 profile 确实存在时，界面才显示“使用已保存密钥重新检查”。密钥只在用户输入和提交期间短暂存在于 renderer，随后保存进操作系统凭据库。提供方订阅、注册与计费仍由其官方网站负责。

目录回执只证明已鉴权发现，一令牌验证也只证明一个精确文本请求到达终止响应；二者都不证明余额充足、所有公布能力可用或生产任务质量合格。因此安装包验收仍须在目标设备上使用测试专用凭据，实际验证每条必需路由和能力，候选安装包才能通过。

## 测试

服务与 renderer 测试覆盖五个产品提供方、中转站动态目录采用、全部刷新的版本提交顺序、验证后提交、密钥脱敏、事务回滚、不支持 `/models` 的自定义端点、一令牌请求前的用户确认、目录未变时复用、换 Key 和模型下线时失效、刷新失败清空、当前模型发送阻止、四态能力展示和底部常驻刷新命令。Host-admission 测试会改写或删除每一项必需模型绑定，并要求启动被拒绝。真实提供方和打包设备回执仍属于发布证据，不能由单元测试替代。
