# Agent Note: 共创全局策略执行边界

Status: implemented

[English](2026-08-17-gongchuang-global-policy-execution-boundaries.md) | 中文

## Problem

共创签名策略门禁最初把首轮步骤和工具策略监听器注册在插件局部 Cordis 上下文中。通过该上下文直接分发的单元测试能够通过，但打包后的 macOS 隔离验收证明：真实子智能体会话在门禁故障注入生效时，仍可能回答纯文本首轮请求。签名策略已经正确装载，问题在于局部监听作用域不足以作为产品信任边界。

## Decision

同一份已验签策略现在固定在三个全局执行边界：

1. 前置的全局 `llm/stream` 监听器在模型适配器收到请求前的最后一个同进程边界，检查签名提供方允许清单。
2. 既有 `agent/pre-step` 监听器改为全局且前置，使专业路由、证据状态和验收故障覆盖子智能体的首轮及后续步骤。
3. 工具分发保留全局前置的 `tools/pre-execute` 策略，并增加单调 `tools.guard()` 拒绝器，对无智能体归属、明确禁止或未知工具保持拒绝。后续插件不能把这个拒绝改成允许。

隔离的 `GONGCHUANG_ACCEPTANCE_GATE_FAULT=pre-step` 模式只能抛错或拒绝。没有通过校验的临时验收数据根目录时，普通启动会拒绝该模式；正常产品组合中不包含该故障配置。

专业提示路由有意比运行时准入更窄。“体检”“评分”“出报告”等有歧义的词，只有在同一请求同时指向企业、政策申报、知识产权、财务或同行等业务主体时，才会启用专业执行链。“给客户端做工程体检”等技术请求继续作为普通产品研发对话处理。若模型在后续步骤实际调用了业务技能，该技能的签名依赖链和交付要求仍会从调用时开始生效。

宿主还会从用户可执行请求中派生唯一回答深度：`query`、`analysis` 或 `formal`。单点问题只给最短充分答案，局部分析只覆盖用户点明的维度，只有明确要求文件或完整报告时才启用签名交付画像的全部标记。业务术语和运行时技能激活本身不会提高深度；正式文件激活会把当前轮次提升为 `formal`，因此其他执行路径不能绕过完整交付要求。

## 备选方案

- 任何业务词出现都进入专业链。它能保护业务任务，但会误伤普通工程和产品支持对话。
- 完全取消提示路由，只依靠模型自行选择技能。它减少误判，但会让明确的业务请求在缺少专业上下文的情况下开始执行。
- 保留“业务主体限定”的提示路由，并结合运行时技能观察。最终采用这一方案：明确业务请求在模型首步前受保护，特殊措辞则在实际选择业务技能时补上保护。
- 对每个专业答案强制使用全部正式交付标记。它保留了最完整的结构，却会把窄问题扩张为报告，还会让无关交付画像拒绝本来有效的简短回答。
- 由每个技能独立决定回答深度。多个技能参与时会产生冲突结构，后续技能调用还可能在用户没有要求时扩张答案。

## Verification

打包后的 macOS 客户端使用空白隔离用户数据启动，并且没有配置 OpenCode Go 凭据。发送纯文本消息后，轮次在产生 `request/header`、凭据读取、助手消息或工具事件之前，以中文失败关闭错误结束；重新打开该会话后失败状态仍然存在。实机回执位于 `acceptance/policy-runtime-outage-live-20260817/receipt.json`。宿主组合测试覆盖三档回答深度，包括不要求完整企业画像标记的单项专利适配问题，以及重新启用完整签名交付画像的正式文件路径。

## Consequences

提示词、`AGENTS.md`、技能和 hooks 仍用于塑造专业行为，但不再承担最终执行约束。提供方准入、首轮策略、工具准入和回答深度均位于签名 Host 控制的运行时边界。简短专业回答仍保留事实、计算、政策来源、完整性和权限检查，但不再附加用户未要求的报告结构。以后新增任何提供方或工具路由，都必须同时满足相关边界，并增加集成测试和打包应用故障注入验收。新增有歧义的专业触发词时，必须同时增加一个带业务主体的正向用例和一个非业务反例。
