# Agent Note: 共创客户端启动清理与 UTF-8 诊断

Status: implemented

[English](2026-08-23-gongchuang-desktop-startup-cleanup-and-utf8-diagnostics.md) | 中文

## 问题

V0.2.2 客户端在新版签名技能包已经内嵌后，仍可能在 `skill-updates/state.json` 中保留陈旧的 V1.6.8 启用失败记录；中断或完成的下载还可能在 `staging` 下留下 12.5 MiB 的 `skill-suite.zip`。Windows PowerShell 5.1 和旧式日志阅读器会把不带 BOM 的 UTF-8 中文按当前 ANSI 代码页解释，导致验收输出与主窗口标题日志出现乱码。主人报告的 Windows 设备还在启动时使用约 97 秒验证包含 10,508 个文件的签名运行时，因为目录分类和文件读取完全同步执行。

这些现象分别归属于启动阶段的不同职责。内嵌技能包负责判断旧更新失败是否仍可处理，更新器负责暂存下载，桌面宿主负责诊断编码，运行时验证器负责在不放宽签名文件约定的前提下管理启动 I/O。

## 决策

技能更新失败记录精确的失败语义版本。`resolveSkillBundleForLaunch` 负责选择并验签生效技能包，但不会在该技能包真正启动前清除旧错误。完整运行时启动成功后，`commitSkillBundleLaunch` 对每次启动执行对账，记录 `lastSuccessVersion` 和 `enabledAt`，清除不高于当前生效版本的错误，并保留严格更新版本的失败与下载状态。状态文件以 UTF-8 原子重写，因此一次成功启动也会把旧 ANSI 或 GBK 错误记录替换为规范 UTF-8 JSON。

下载的 ZIP 字节只在内存中完成验证与解压，不再向暂存目录写入 `skill-suite.zip`。验签成功的下载事务在技能包成功启动前保留 UTF-8 `activation-receipt.json`。启动成功并完成状态对账后，宿主通过 Electron 的可恢复操作系统废纸篓或回收站 API 移走当前生效版本带成功回执的事务及全部更旧的历史暂存事务。当前版本或更新版本的失败事务继续保留，供重试和诊断。已安装的 `versions/*` 目录永远不是清理目标，继续保留作恢复用途。

桌面宿主在写入第一条应用日志前给 `main.log` 添加 UTF-8 BOM，并在日志轮换后再次准备新日志。Windows 验收 PowerShell 脚本自身带有 UTF-8 BOM，控制台输入与输出编码均设为 UTF-8，并以 UTF-8 显式读取 JSON 清单。产品中文保持 Unicode，不转码为 GBK。

启动运行时验证仍检查 Ed25519 签名、固定公钥指纹、产品身份、版本、平台、架构、签名层级、精确文件与链接集合、每个文件的 SHA-256、可执行文件身份、PaddleOCR MCP 和文档依赖闭包。目录遍历改用 `Dirent` 元数据，启动文件哈希改用由 `availableParallelism()` 决定的有界工作协程。同步验证器继续供打包和发布脚本使用。

## 验证

单元测试复现 V1.6.8 失败记录、旧版本目录、暂存 ZIP 和旧式非 UTF-8 错误字节。测试证明记录在 V1.6.9 完整启动前保持不变，启动成功后改写为 UTF-8 成功状态，同时已安装的 V1.6.8 目录仍然保留。下载测试证明验签成功事务带有成功回执且不落盘 ZIP，成功与历史事务进入可恢复测试回收站，当前或更新版本的失败事务继续保留。其他测试分别固定新旧日志恰好一个 BOM、PowerShell UTF-8 信封、并发运行时正常验证和文件篡改后的失败关闭行为。

在现有 formal 签名的 Windows x64 运行时副本上，两条验证路径接受了相同的 10,508 个文件和同一索引 SHA-256。首次本机同步运行约 1,092 ms，并发运行约 350 ms；热缓存运行分别约 371 ms 和 345 ms。该测量证明本机路径改善且身份一致，不能代替主人所报 Windows 设备的冷启动结果。必须由该设备测量 V0.2.3 候选后，才能把 97 秒缺陷记为生产闭合。

## 备选方案

**首次启动通过后缓存或跳过完整文件树验证。** 未采用，因为磁盘损坏、杀毒软件隔离或文件修改都可能让运行时在两次启动之间发生漂移。缓存会削弱已有完整性边界，也不能证明当前字节。

**只验证可执行文件或抽样验证运行时文件。** 未采用，因为 Python 源码、元数据、许可证和导入模块都是签名运行时约定的一部分。抽样会把精确完整性降级为概率发现。

**启动后把全部暂存目录和已安装版本移入回收站。** 未采用，因为失败暂存需要支持重试与诊断，已安装版本需要保留恢复材料。只有成功或已经被更新版本取代的暂存事务可以清理，而且仍须通过操作系统废纸篓或回收站实现可恢复清理。

**内嵌技能包一通过验签就清除旧错误。** 未采用，因为验签通过并不能证明完整运行时能够用该技能包成功启动。只有运行时启动成功返回后才提交成功状态。

**在 Windows 上把日志和脚本写成 GBK。** 未采用，因为 GBK 不能稳定表示产品的完整 Unicode 文本，还会产生平台专属诊断格式。UTF-8 BOM 能消除旧式阅读器的编码歧义，同时保持跨平台统一编码。

## 影响

同版本或更新技能包成功启动后，已经失效的失败状态不会继续残留，真实的更新版本失败仍保持可见。升级后历史暂存不会继续堆积，但当前失败事务和已安装回滚版本会占用磁盘，直至后续成功升级或用户执行恢复操作。中文诊断和状态文件统一使用 UTF-8，识别 BOM 的旧式编辑器也能正确打开主日志。启动仍执行完整的密码学与文件集合检查，只是减少文件系统往返并重叠读取；代价是技能下载归档会保留在内存中，运行时会同时读取若干文件。Windows 冷启动的实际改善仍属于候选验收测量，不能仅凭源码断言。
