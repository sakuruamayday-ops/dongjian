# Agent Note: 桌面技能更新发布闭环

Status: implemented

[English](2026-09-02-desktop-skill-update-release-closure.md) | 中文

## Problem

桌面客户端与独立发布的技能套件具有不同的版本生命周期，但一次技能正式发布可以在 GitHub、知识门户和本机安装全部完成，却没有推进桌面更新源。此时即使存在更高版本的正式套件，客户端仍会正确地把随包套件显示为最新版。通用分发包带有外层目录且使用不同的投影合同，不能直接修复该更新源。首次恢复构建还带入了仅供内嵌套件使用的 `config/common.yaml`；服务端签名检查接受了该文件，而已发布的 V0.4.1 更新器会拒绝这个额外根目录项。

## Decision

独立桌面更新从 formal 客户端投影构建，并显式指定预期版本。ZIP 只包含 `skill-bundle-index.json`、`skill-bundle-index.sig`、`skill-bundle-index.pub.pem`、`staging-receipt.json`，以及签名索引在 `skills/` 下声明的文件。仅供内嵌套件使用的资源不进入该归档。

每次包含通用包的技能正式发布都把这份桌面归档作为签名发布事务中的独立参与方。通用门户发布、GitHub 发布和本机同步成功后，服务器发布器先核验事务绑定、固定的 Ed25519 公钥、版本、完整文件清单和已经存在的门户通用正式版，再原子推进桌面更新源。随后发布命令重新下载公网清单与准确归档，对照事务绑定的摘要，并使用同一归档校验器验证，全部通过后才能完成。

已发布客户端仍是最终兼容性权威。因此恢复和回归验收会使用 V0.4.1 的 `SkillUpdaterController` 完整执行发现、下载、校验、激活准备与提交；只通过服务端校验并不足以证明客户端可用。本决策扩展了[共创聚焦式侧栏与桌面设置](../feature/2026-08-15-gongchuang-focused-sidebar-and-desktop-settings.zh.md)中记录的独立更新边界。

设置页通过独立的只读桌面 IPC 读取当前本地技能包。在线发现不能在读取活动套件失败时用编译期内置版本替代。包括 HTTP 404 在内的发现失败表示来源不可用，不能证明已安装套件就是最新版；此前已知的安装版本仍可显示，但不得展示绿色“已是最新”。

独立 ZIP 生成会把条目时间固定为 ZIP 纪元对应的本地 DOS 时间，使相同签名输入在不同时区构建仍得到相同字节。服务器从读取 `latest.json`、检查不可变归档到原子替换清单的全过程持有同一个通道级文件锁；按版本租约无法串行化不同版本竞争同一共享指针。锁文件保持存在，避免竞争方获取不同 inode。

设备验收从发行配置或显式清单参数读取候选技能身份，两个平台的运行器都不会默认使用上次发布的技能版本或文件数量。产品身份测试还会在发布事务成功前区分候选与仍然生效的正式版。

## Alternatives considered

**每次发布后手动推进更新源。** 不采用，因为 V1.6.13 至 V1.6.16 的更新源遗漏已经证明，游离于正式事务之外的后续步骤会静默漂移。

**把 GitHub 通用 ZIP 直接提供给客户端。** 不采用，因为它的外层目录、独立分发内容和签名边界均不符合桌面更新器合同。

**接受暂存目录中的所有文件。** 不采用，因为 V0.4.1 消费方有意采用封闭归档形态；加入未签名或仅供内嵌套件使用的根级资源，会让有效下载变成无法安装的更新。

## Consequences

后续技能正式发布若没有独立签名的桌面投影和成功的公网回读，就不能完成。相同版本的归档不可变，更新源也禁止降级。发布方需要多构建一个产物并保留事务证据，但客户端无需发布新二进制即可发现更新。公网更新源仍是可用性依赖，而签名和文件清单核验继续作为本机失败关闭保护。

2026-09-03 的本地修正与历史 V0.4.1 发布回执分别测试。本地控制器、浏览器、可复现归档和并发发布结果都不构成新的已部署客户端或服务器发行。
