# Agent Note: 模型连接持久化语义

Status: implemented

[English](2026-08-31-model-connection-persistence-semantics.md) | 中文

## 问题

模型连接配置、模型选择和默认模型持久化是三次不同的提交。此前有三条路径混淆了这些边界。启动时提供方探测短暂失败，可能自动选择并持久化另一个已就绪提供方；会话模型选择在默认设置写入失败后仍返回成功；连接配置已经提交新端点与凭据后，后续自动选择失败却会被表现为整次配置失败。

这些路径会让重启看起来恢复了旧模型，也会在新连接其实已经保存时造成界面与 Host 状态不一致。

## 决策

启动对账只要发现持久化活动路由仍能映射到产品提供方，就继续保留该提供方，包括 `loading`、`error`、`missing` 和 `unavailable` 状态；只有该路由处于 `ready` 时才自动执行选择。仅当持久化路由已经无法映射到任何产品提供方时，才使用既有的已就绪提供方回退。因此，短暂探测或凭据库状态误分类都不能改写持久化选择。

会话模型选择现在先持久化跨会话默认值，再追加会话局部的 `model/selection` 事件。默认值写入失败时，Remote 返回可观察错误，并保持会话日志不变。客户端不能再声称完成了一次新会话无法恢复的持久切换。

提供方配置在自动选择失败时保留已经提交的连接。产品返回部分成功结果；凭据已经由 Host 保护，因此清空渲染进程中的密码输入框；同时展示“连接已保存，自动切换失败”和可操作的选择错误，不把已验证连接重新标成未保存。

模型目录发现与真实调用共用已提交的凭据引用、端点和协议。官方 DeepSeek 配置会写入适配器所需的三个输入，回滚则连同目录一起恢复先前连接。托管预设刷新会用注册表值替换旧凭据名称和过期固定端点，同时保留用户已经批准的可选或必需端点。刷新后，没有远程目录的手工模型仍保持 `candidate`；本地适配器目录不能证明远程鉴权成功。画像回滚失败不能跳过凭据补偿，也不能让提供方永久停在 `checking`。

## 曾考虑的替代方案

**当前提供方未就绪时选择第一个已就绪提供方。** 不采用，因为临时网络、余额、凭据库可用性，甚至可修复的凭据缺失都不代表用户意图，不能覆盖持久化路由。

**会话选择继续成功，只记录默认写入失败日志。** 不采用，因为日志不是用户可观察的产品契约，之后的新会话会静默使用另一个默认值。

**自动选择失败时回滚已经验证的连接。** 不采用，因为端点与凭据提交已经成功，用户可以直接选择或重试，无需再次输入密钥。

## 后果

重启行为在提供方短暂失败时继续遵循用户的持久化意图。模型选择 Remote 返回成功时，默认值与会话选择意图都已接受。连接配置仍可独立于自动选择成功，界面会准确说明部分成功，并且不保留或暴露已经提交的 API Key。

回归测试覆盖启动瞬时状态、默认写入拒绝且不产生会话事件，以及连接已保存后的可见部分成功。

同 ID 的 DeepSeek 目录项会更新明确提供的新名称和容量，同时保留既有可信能力与本次省略的元数据。配置和刷新都会把这些值传入真实适配器，而不只更新设置页。画像或凭据恢复不完整时，独立补偿会向用户报告残留的新配置，不会静默隐藏。

真实适配器测试还覆盖密钥替换、旧凭据名称、端点与协议修正，以及从持久配置重新挂载的运行时。故障注入覆盖目录采用、画像与凭据分别回滚失败及刷新恢复。测试中的网络响应是受控夹具，不能证明真实提供方账号或新发布桌面二进制可用。
