# 共创企业助手 PDF 渲染与底座升级设计

状态：当前生产版 V0.4.1 已于 2026-09-02 从精确源 `eac8855411044f6445a82b04a3e5aad1c25689e7` 通过受控门户和 V0.2 分平台更新源正式发布，服务器 release_id=18；内嵌 formal V1.6.15。当前底座为 `dsh-v0.1.2-alpha.4` 的不可变提交 `4e84901e6471b79ec0338099867ebb4606d12bb5`；早期 alpha 候选只作历史诊断，不改变默认 Word、按需 PDF 与同源渲染方案。

2026-08-23 发布后审查已将 PDF 同源预览限制为单文档 32 MiB、总缓存 64 MiB 和 32 条记录，并在自动比较开始时消耗匹配预览；更新只在显式操作且安装前关闭成功后执行。两项修复已随 V0.2.1 发布。随后主人取消逐模型选择探针、验证状态和技术能力标签；V0.2.2 只在客户端启动和用户点击“刷新模型”时刷新目录，打开或切换模型不联网、不验证、不消耗额外 token。V0.2.3 不改变 PDF、报告模式或模型交互，只修复技能更新残留、Windows UTF-8 诊断和启动完整验签耗时。V0.2.4 在这一无探针边界内发布模型搜索、提供方折叠和桌面原生编辑右键菜单，同时收口文件草稿、Windows 关闭偏好、账号恢复、MCP 并行启动、Windows 语言包减重、版本基线和专业回答深度。V0.2.5 不改变 PDF 生成方案，修复 Office/XLS 读取、证据显示值、机器回执与专业文件发布顺序。V0.2.6 修复 macOS 自更新对目标版本的验签语义、失败诊断和可恢复暂存清理；V0.2.7 不改变报告、PDF 或 Windows 安装机制，继续收束运行时写入面、启动修复和 Windows 启动开销；V0.2.8 同样不改变 PDF 方案，只补齐当前会话附件取消引用和多层循环收敛。V0.2.9 把附件移入会话级待发送状态，并增加运行期脱敏日志、XLSX 显示值和天眼查官方设备授权；V0.3.0 与 V0.3.1 继续保持报告与 PDF 方案不变。V0.3.2 仍默认 Word、按需 PDF，只把 Host Retina 截图归一到标准 A4 像素后再做差异计算。V0.3.3 同样不改变报告与 PDF 方案，只收口更新恢复、归档和自动任务会话。

## 2. 已核验的 V0.1.4 基线

V0.1.4 于 2026-08-21 从 `7a3ec0be4125030c7aa318470473ee65bc090ad2` 发布，内嵌 formal V1.6.8 技能投影。macOS arm64、macOS x64 与 Windows x64 运行时包含 Python 和文档依赖，但不包含 LibreOffice。

| 能力 | 当前实现 | V0.1.4 结果 |
| --- | --- | --- |
| DOCX 生成 | `python-docx` 直接写入 OOXML | 可用并完成结构性重开 |
| XLSX 生成 | `openpyxl` 与 XlsxWriter 直接写入 OOXML | 可用并完成结构性重开 |
| PPTX 生成 | `python-pptx` 与 Pillow 直接写入 OOXML | 可用并完成结构性重开 |
| 基础 PDF 生成与解析 | 随包 PyMuPDF 1.28.2 创建并重开 PDF 字节 | 打包 Python 可直接使用，用户无需安装，但不等于版式渲染验收 |
| 技能专用排版 PDF | 部分独立技能使用 HTML 源、Playwright 调用 Chromium，再经 PyMuPDF 加品牌 | 个别技能脚本中存在，但未绑定为桌面宿主渲染器 |
| 官方 PDF 导出工具 | `gongchuang_render_pdf` 调用 `gongchuangArtifactRenderer.exportPdf` | 桌面宿主没有提供实现，保持关闭 |
| PDF 正文解析 | 专业校验器调用 `gongchuangArtifactRenderer.inspectPdf` | 因同一宿主实现缺失而关闭 |
| 逐页渲染与视觉验收 | 专业校验器调用 `gongchuangArtifactRenderer.renderAndReview` | 因同一宿主实现缺失而关闭 |
| LibreOffice 转换 | 暂存运行时没有 LibreOffice 可执行文件或资源 | V0.1.4 打包范围有意排除 |

因此，当前并不是所有文档都走 HTML。Office 文件采用 OOXML 直接生成，基础 PDF 可由 PyMuPDF 生成，部分排版报告技能以 HTML 为中间稿。官方宿主 PDF 导出和视觉验收不可用，是因为消费接口已经存在，但宿主提供者没有实现。

PyMuPDF 以固定平台 wheel 的形式进入 macOS arm64、macOS x64 和 Windows x64 的签名产品运行时。用户不得额外安装 Python、`pip` 或 PyMuPDF。随包模块缺失或损坏属于客户端完整性故障：对应能力保持不可用，通过修复或更新客户端恢复，不得临时解析任意系统包。

主人于 2026-08-23 确认 V0.2.0 macOS arm64、macOS x64 与 Windows x64 三端实际测试均已通过。macOS x64 的仓库回执仍只证明 Rosetta；Windows 没有结构化步骤回执，因此不补造 SmartScreen、安装、更新或卸载的具体子步骤。Windows 安装器和主程序仍未签名。

## 3. 根因

`GongchuangArtifactRenderer` 定义了 PDF 解析、导出和逐页复核方法，策略插件也注册了消费这些方法的工具，但桌面端没有任何包调用 `ctx.provide('gongchuangArtifactRenderer', ...)`。生产证据使用的是测试替身，不是组装后的打包宿主实现，因此运行时能力没有闭合。

固定渲染器身份 `gongchuang-electron-libreoffice-v1` 还声称使用 LibreOffice，而 V0.1.4 实际没有携带 LibreOffice。修复后的实现必须使用准确描述真实引擎的新版本身份，不能为了兼容继续保留这个误导性名称。

## 4. PDF 能力模型提案

以下术语作为本设计的规范用语：

- **PDF 源文件**：用于生成 PDF 的不可变 HTML 或受支持文档文件。
- **PDF 导出**：从一个已绑定源文件生成最终 PDF 字节，且不得覆盖既有文件。
- **PDF 正文解析**：从最终 PDF 的精确字节提取页数和规范化正文。
- **逐页栅格化**：把最终 PDF 的每一页转换为受限 PNG 预览，并记录页码、尺寸和摘要。
- **自动视觉回归**：把最终 PDF 的完整逐页栅格化结果与来源明确的参考图像自动比较；它只报告渲染变化，不包含人工决定，也不得产生 `user-confirmed` 回执。

已确认的架构是在已签名桌面宿主中提供实现：本机 HTML 源由 Electron Chromium `printToPDF` 生成 PDF，PDF 正文解析、品牌处理和逐页栅格化由随包 PyMuPDF 完成。DOCX、XLSX 和 PPTX 继续直接生成 OOXML，不为 PDF 输出单独恢复 LibreOffice。

报告产物默认为一份可编辑 DOCX；只有用户明确要求 PDF 时，才从同一份定稿内容导出 PDF，不进行第二轮模型写作。企业全景 A／B／C 以及项目预评估、可行性和双报告选择属于业务模式，与 DOCX／PDF 格式无关并完整保留。

第二轮决定进一步固定以下边界：

- 自动视觉回归只作用于最终 PDF；Office 产物继续接受结构、内容、可打开性验收，不引入 Office 转 PDF 图像比较门禁。下一版本不提供人工逐页接受或拒绝流程。
- macOS arm64 与 x64 随包携带经审查、版本固定且许可可分发的确定性中文字体。缺字或未经认可的系统字体回退必须显式失败，不得静默改变版式。
- HTML 导出只接受企业空间内的静态 HTML、CSS 和本地媒体资源；禁止联网和脚本执行。图表在进入渲染器前预生成为受控 SVG 或 PNG。
- 自动视觉回归使用分层参考：固定黄金样例的逐页参考用于跨版本和跨平台回归；实际动态 PDF 另与同源打印布局预览比较，只证明导出链一致，不证明业务内容正确或专业质量合格。
- 自动视觉回归超出已记录容差时阻止发布候选，并生成逐页差异图；不采用只警告或零像素差异方案。具体容差必须由固定样例和 macOS 双架构测量确定，不能写成未经测量的常量。

## 5. DeepSeek Harness 升级基线

当前产品声明使用 DeepSeek Harness `0.1.0-rc.8`。官方 RC.8 标签实际对应 `141eb6fef83422698aef7a981029e843e8161534`；现有兼容矩阵误写为不存在的 `...1531`。

截至 2026-08-22 核验到的最新不可变上游预发布版本是 [`dsh-v0.1.1-rc.2`](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.1-rc.2)，提交为 `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`。RC.1 新增 DeepSeek 实验性视觉模型、Bubblewrap 逃逸修复、多行提问、会话与界面修复和鉴权调整；RC.2 统一图像接入链，增加 Files API 上传与复用，并按模型要求改进图像预处理。

本地三方差异审计显示，从 RC.8 到 RC.2 包含 207 个上游提交和 2416 个变更文件。共创分支从同一基线形成 25 个提交和 840 个变更文件，双方重叠 189 个路径，主要集中在会话界面、宿主 API、Web 启动、会话投影、模型适配、附件处理和文档生成器。因此本次升级属于适配项目，不是修改版本字符串。

已确认的目标是不可变的 RC.2 标签，而不是上游 `master`。升级按能力层推进：先验证纯上游，再处理启动与模块组装、宿主 API、会话与对话界面、模型与图像适配、共创插槽与策略，最后取得打包客户端证据。

主人确认把 Vision 与 Files API 拆分。下一版本向产品开放的是提供方无关的视觉模型路由：任何明确声明图片输入且通过真实服务验收的模型都可使用；切换到纯文本模型时必须明确说明不能读取图片。DeepSeek Files API 只是 `deepseek-official` 路由优先采用的内部提供方文件传输，不作为单独功能或开关，也不能把 DeepSeek `file_id` 交给其他提供方复用。其他视觉提供方使用各自适配器支持的图片传输或受限内联路径。

第三轮按推荐方案确认每个提供方首次使用图片前集中告知与同意，DeepSeek 远端图片默认保留一小时，可选七天或三十天；每次发送保持清晰的远端提供方标识，设置页提供删除远端文件和清理本地映射。该选择仍要求真实 DeepSeek 与至少一条非 DeepSeek 视觉路由验收。

V0.1.4 的模型目录存在两套来源。连接模块会在启动后台、手动重新检查、凭据或适配器变化时直接请求提供方 `/models`，但在线结果只进入连接回执中的模型数量和单个推荐模型；模型选择器仍读取随适配器安装的静态目录。OpenCode Go 的未知模型会被本地拒绝，DeepSeek 的未知模型虽然可由底层按纯文本 ID 发送，却进不了正常产品选择流；自定义兼容 API 可以重新保存一个文本模型 ID，但不会自动吸收端点新增模型。提供方删除或改名当前模型时，连接回执和当前会话还可能分叉，直到本地或服务端报错。

第四轮最初决定在启动后台、打开选择器、网络恢复和用户手动刷新时更新目录。V0.2.2 根据主人后续明确纠正收窄为：Host 在客户端启动时刷新一次，此后只有用户点击“刷新模型”才刷新；打开选择器、切换模型、切换推理强度和网络恢复都不触发目录刷新。产品仍不引入共创服务器、团队知识库或团队模型目录；连接状态与模型选择器读取同一份 Host 投影，普通 OpenAI 兼容文本模型新增后无需发布客户端即可被发现。

刷新与目录查找交互参考 Hermes Agent GitHub 上游当前模型目录：底部常驻显示“刷新模型”，刷新期间防止重复触发并更新当前会话和配置作用域；搜索只过滤驻留目录，提供方标题可独立折叠，搜索期间临时展开命中项且清空后恢复原折叠状态。共创企业助手不采用 Hermes 在失败后继续保留缓存目录的降级；按已确认产品决定，人工刷新失败后清空选择器并显示“目录暂不可用”。OpenCode Go、硅基流动与 Orgarid 都按中转站路由执行同一套动态刷新。

第五轮最初决定在首次选择新文本候选时，经确认发送最小真实服务请求。V0.2.2 已取消这一逐模型探针：选择模型或推理强度只提交当前会话选择，不发送 `只回复 OK` 或其他验证请求，也不建立验证缓存。所选模型能否使用由用户的正常对话请求证明；失败时如实提示，用户自行重试、刷新目录或切换模型。

不支持 `/models` 的自定义兼容端点仍允许手填精确模型 ID；配置阶段负责凭据与路由可用性，选择阶段不再把它标成“待验证”或发送最小请求。图片输入、推理强度和提供方文件传输继续以已安装适配器的精确目录为准，不能根据模型名称猜测。能力撤回时保留草稿和附件，并提示切换模型或改为纯文本，不能静默丢弃内容或参数。

V0.2.2 删除验证结果缓存、首次确认弹窗和选择器里的已验证、待验证、同步时间及文本、图片、推理、文件标签。模型列表只显示提供方、模型名、选中标记和底部刷新命令；推理强度在已安装精确模型目录声明时作为独立选项显示。OpenCode Go DeepSeek V4 Pro 继承适配器目录并恢复 `off/high/max`。V0.4.0 更新到官方 `pi-ai` 0.84.4 后，DeepSeek V4 Flash Vision Exp 同样从精确目录获得图像输入与 `off/low/high/max`，不新增产品自有的模型名推断规则。

主人决定不拆分修复版与底座升级版。V0.2.0 同时包含 RC.2、PDF 宿主渲染器、自动视觉回归、提供方无关 Vision、DeepSeek Files、动态模型目录、选文续问修复、专业循环收敛、Mac DMG 直接覆盖安装和 Windows x64 发布。业务功能仍按一个版本验收；Windows 缺少签名与新版真机回执则作为主人明确接受的发布限制披露。

设计收口采用以下发布默认值：正式版本号为 V0.2.0；macOS arm64 与 macOS x64 属于同一源提交和统一验收矩阵，任一必需证据未通过时不切换 Mac 正式更新源；Windows x64 以另一精确发布提交构建并单独记录静态验收和风险边界。本范围不预先安排中途热修，若出现安全或数据损坏紧急情况，必须另行形成明确授权和独立发布边界。

V0.2.0 的安装资产不发布到 GitHub Release，GitHub Latest 也不参与版本发现、发布批准或回滚。受控门户负责 Mac DMG 与 Windows NSIS 下载，`https://zshjiaotang.cn/client-updates/v0.2/` 下的分平台清单与产物是 V0.2.0 后续更新权威。Mac 仍使用签名清单；Windows 当前发布物为未签名风险接受包，不能把包内运行时和技能 Ed25519 验签误写成 Authenticode。

## 6. 设计闭环与发布结果

| V0.2.0 设计期遗漏 | 已形成的设计结论 |
| --- | --- |
| 缺少渲染器提供者 | 明确服务定义、签名宿主提供者、界面消费者、生命周期和失败行为 |
| LibreOffice 渲染器身份与实际不符 | 引入准确描述真实引擎的版本化回执身份，并明确兼容处理 |
| 渲染器组装仅有模拟证据 | 增加桌面端真实组装测试和打包候选执行回执 |
| 确定性字体落地待实现 | 按已确认方案随包携带经审查的固定中文字体，并验证许可、缺字失败和 macOS 双架构一致性 |
| HTML 导出隔离待实现 | 按已确认方案只接受企业空间内静态 HTML/CSS/媒体，禁止联网与脚本，图表预渲染为受控 SVG/PNG |
| 自动视觉回归分层参考待落实 | 固定黄金样例用于跨版本和跨平台回归；动态 PDF 与同源打印布局预览比较时只判定导出链一致性，不声称内容正确 |
| Office 验收边界待落实 | 按已确认方案仅对最终 PDF 做自动图像比较；Office 保持结构、内容和可打开性验收 |
| 上游固定提交写错 | 在记录新目标前先把 `...1531` 更正为官方 `...1534` |
| 上游重叠面大 | 建立逐路径的保留、采用上游、适配和退役台账 |
| 新视觉模型数据路径 | 按已确认方案开放提供方无关视觉路由，将 DeepSeek Files 保持为内部传输，并实现首次同意、默认一小时保留、清理、降级和真实服务验收 |
| 在线模型目录与选择器断链 | 连接状态与选择器共用 Host 目录投影；启动刷新一次，之后只响应用户明确刷新，不经过共创服务器 |

## 7. 客户端自更新兼容性审计

当前产品提供的是“自动检查更新＋用户确认的一键自更新”：客户端在启动后检查一次客户端与技能更新，随后每六小时非阻塞检查；发现版本后只提示，不静默下载或安装，用户点击“立即更新”后才进入安装流程。2026-08-22 的 3 个文件、50 项定向回归以及 V0.2.4、V0.2.5 发布演练都使用目标源码控制器或模拟验证函数，没有执行对应已发布旧版二进制，因此没有覆盖真实跨版本缺口。

| --- | --- | --- |

## 8. 对话循环收敛审计

V0.1.4 只修复了一个窄场景：对 HTML 或 Office 等非 PDF 正式件，宿主缺少逐页渲染器时，策略只注入一次限制提示，不再把 `visual-inspection` 当作可重试回执；其他可执行回执补齐后可以结束。该修复已进入 V0.1.4 发布源。

专业 PDF 并未因此闭合。当前 PDF 正文解析、专业校验、品牌处理和逐页视觉回执都依赖同一个宿主渲染器；宿主缺失时，策略只豁免 `visual-inspection`，不会豁免其余无法生成的回执，因此仍会在同一轮重复纠正。当前代码还有两个确定风险：同轮先写 HTML 源再导出 PDF 会把源与最终文件累计为两个正式产物，且该集合在本轮无法清除；新方案的 Electron、PyMuPDF 和自动图像比较也与旧回执中写死的 LibreOffice 身份及 `user-confirmed` 状态不兼容，若不同步迁移契约会形成新的永久失败。

Agent Loop 没有内建总步数预算；策略中的 `maxSteps` 只收束联网检索，不限制专业纠正续步。缺少必需技能、未选定具体路由、质量门禁顺序错误、回执生产者不可用、已验证候选与最终回答持续漂移、文件未绑定或持续变化等条件，都会在每次停止时再次注入纠正消息。现有 149 项相关测试全部通过，但测试使用假的 `steer` 或人工补齐状态，没有把真实 Agent Loop 运行到结束，也没有证明不可达条件能在有界步数内停止。

因此，准确结论是：V0.1.4 没有彻底解决主人所说的循环卡死，专业 PDF 和其他不可达专业门禁仍可能触发。下一版由共创专业策略拥有有界收敛，不给通用 Agent Loop 添加无条件全局截断；能力不可用或不可恢复的问题立即以用户可见的“未完成”结果结束，可修复问题若同一问题集合连续两次没有实质进展或本轮累计四次纠正仍未完成，也必须失败关闭并结束轮次。停止时保留会话和文件，不得伪造专业验证或文件验收成功。

V0.4.0 将归档与删除彻底分开。归档继续保留并可恢复；删除只接受 workspaceId 或 sessionId，由桌面 Host 从权威注册表和持久层解析路径，在会话 `flush → dispose → persistence retirement` 后把企业目录或会话日志移入系统废纸篓。持久 pending intent 记录已解析的会话集合和目标路径，使部分移动、进程退出、日志已消失或 journal 收尾失败都能在下次启动续办；会话删除屏障阻止自动任务或其他恢复路径在停机后重新创建 writer，只有 Trash 前的完整事务回滚才释放。系统根、用户关键目录、当前企业根、安装目录、符号链接替换、注册空间嵌套和过宽历史路径全部失败关闭。

模型刷新仍只发生在首次启动和用户显式点击刷新。Host 把凭据解析和目录异常限制在单个提供方，失败项保留刷新前的配置、模型数和选择状态并发布错误，后续提供方继续刷新；Client 只有在远端整体失败、读取失败或已配置目录没有任何模型时才清空全局结果。OpenCode Go 与其他中转站继续使用同一提供方目录机制，切换模型不探针、不验证。

正式文件发布改用结构化回执生成可点击的产出文件卡，不从自然语言推断路径；显式发布存在时隐藏中间产物，点击仍由 Host 做安全打开。技能内容被会话裁剪后，同一直接用户轮次只精确重载一次，重复裁剪明确复用已加载内容，不形成技能或深度澄清循环。桌面同时补齐跨卷文件导入的排他复制回退、更新接管失败后的旧应用重启、Windows renderer 重载后的关闭提示恢复，以及自动任务长运行与完成回执断线的收敛。

会话展示继续与模型文本分离。每次提交把用户原始正文和本轮受控文档引用组合为独立展示投影；聊天记录按导入顺序在正文上方渲染紧凑文件标签，只有附件时不生成空白正文气泡。标签只显示文件名，只有开头的受控导入引用可变成点击控件，普通行内引用和畸形路径保持普通文字；点击后由 Host 打开工作区导入文件，复制操作只复制用户原始正文。待提交回显、排队、插话和重载历史消费同一投影，产品生成的模型说明不进入可见正文。

macOS 公测首装采用免费人工放行路径，不引入 Developer ID 或公证替代目标。`afterPack` 在 macOS 只验证最终 ASAR 内容，Electron Builder 随后处理 Electron fuses，并以 `mac.identity: "-"` 完成唯一一次原生最终 ad-hoc 签名。产品运行时内的 Mach-O 已带有效签名且其精确字节受 Ed25519 索引约束，因此 `mac.signIgnore` 阻止 Builder 再次改写该目录；外层 App 仍封存运行时资源。只读 `afterSign` 在 DMG 与 ZIP 生成前复验整个 App 的深度签名以及内嵌运行时和技能索引，任何签名顺序造成的字节漂移都停止构建。DMG 与 ZIP 从该 App 直接生成，签名后不得再改包。公开下载保持用户主动点击的普通 DMG 直链，不使用后台下载、Blob 或中转脚本。正式发布前须在干净 macOS 环境从生产域候选直链用 Safari 下载，经 Finder 拖入“应用程序”，记录首次拦截、隐私与安全性中的“仍要打开”、二次确认和放行后 V0.4.0 正常启动。若显示“已损坏”、没有对应按钮或放行后无法启动，统一 V0.4.0 停止发布。上述 UI 通过后，下载页才把 `xattr` 终端说明替换为下载、拖入应用程序、隐私与安全性放行三步图形帮助。
